# Kernel stage 20: the x86-64 target, the second ISA family

*A design note, not a Mark. `plan/kernel-path.md` owns the stage list;
`plan/freestanding.md` owns the freestanding mode; this is what the x86-64
`_start` stub decided and why.*

## Why x86-64 needed a stub at all

QEMU's riscv64 `virt` machine and its aarch64 one both load a 64-bit ELF through
`-kernel` and start it at its entry point with the CPU already in its widest
mode and paging off. x86-64 has no such loader: an x86-64 ELF is entered by
SeaBIOS' Xen PVH support, which scans the image's `PT_NOTE` program headers for
the `XEN_ELFNOTE_PHYS32_ENTRY` note (type 18, owner `Xen`), loads the ELF's
segments, and jumps to the 32-bit physical address the note names **in 32-bit
protected mode with paging off**. Before any Kelp code can run the stub has to
be long mode: a GDT with a 64-bit code segment, a page table, PAE, `EFER.LME`,
`CR0.PG`, and a far jump. That is bootstrapping, not language work, which is
why x86-64 followed the whole stage list rather than preceding riscv64.

## The target

`[target] triple = "x86_64-unknown-none"` (the `-elf` spelling is the same
prefix and is accepted too). `kelpc` loads the X86 backend by name
(`LLVMInitializeX86*`, the same four-plus-parser calls riscv64 and aarch64 use),
then a `TargetMachine` with the `x86-64` CPU, no extra features, the **static**
relocation model and the **small** code model. `small` is what links an image
placed at 1 MiB: `kernel` assumes the code sits in the top 2 GiB of the address
space and `medium` is LLVM's x86-64 default but larger than a 1 MiB image needs,
while `small` reaches code and data in the low 2 GiB with the shortest
addressing. Every emitted function is marked `noredzone`, because the x86-64
System V ABI's 128-byte red zone below `rsp` is clobbered by any interrupt and a
kernel that is about to take one must not keep live values there.

The stub enables SSE itself before it calls Kelp: `CR0.EM` clear and `CR0.MP`
set plus `CR4.OSFXSR` and `CR4.OSXMMEXCPT` set, so LLVM's SSE lowering (a
`memcpy`/struct copy, an `f64`) is safe. Nothing asks the compiler to avoid SSE;
the stub is simply earlier than every generated instruction.

## The boot flow

The x86-64 `_start` is module-level assembly (the same mechanism the riscv64 and
aarch64 stubs use) with one section for the note, one for the 32-bit and 64-bit
code, and one NOBITS section for the boot page tables:

1. `.note.Xen` holds a note (namesz 4, descsz 4, type 18) whose 4-byte
   description is the address of `_start`. It sits in a `PT_NOTE` program
   header, which is where SeaBIOS looks.
2. `_start` starts in `.code32`. It loads a three-entry GDT (null, 64-bit code
   at selector `0x08`, data at `0x10`), zeroes the three boot page-table pages
   in `.boot_pt` (a NOBITS section the later `.bss` clear deliberately does not
   cover), fills PML4[0] with the PDPT, PDPT[0] with one PD, and the PD with 512
   `2 MiB` present+rw+ps entries that identity-map the first 1 GiB, sets
   `CR4.PAE`, sets `EFER.LME` through `rdmsr`/`wrmsr`, loads `CR3`, and sets
   `CR0.PG|CR0.PE`.
3. A far jump (`0xEA` selector `0x08`) into the `.code64` label turns on
   `EFER.LMA`, and the 64-bit half reloads the data segment registers, loads
   `rsp` from `__stack_top`, and zeroes `[__bss_start, __bss_end)` a word at a
   time. The tables live in `.boot_pt`, so this clear never touches them even
   though the clear runs after paging is on and the tables are reachable through
   the identity map.
4. It enables SSE (the CR0/CR4 pair above), sets `MXCSR` to its reset value, and
   `call`s the entry `fun` (`kelp_kmain`). If the entry returns, it spins on
   `hlt`.

`__bss_start` and `__bss_end` are `.weak`, exactly as the other two stubs
declare them, and `halt_asm_template` gained the x86-64 `hlt` for the
double-panic loop.

## The examples

- `examples/kernel0-x86_64/` is a COM1 (0x3F8) driver: poll the Line Status
  Register at 0x3FD for bit 5 (THR empty) through `in`, then write THR at 0x3F8
  through `out`, both inline `asm` in the `uart` module the `[unsafe]` list
  names. `kmain` prints `hello from kelp (x86_64)` and halts. Port I/O is not
  memory-mapped, so the manifest needs no `mmio` grant: `in`/`out` name a port
  number, not a `Ptr.from_addr`.
- `examples/kernel0-x86_64-lmode/` prints that greeting, then reads `CR0`,
  `CR4` and `EFER` through `asm`, prints `long mode on` only when `EFER.LMA`
  (and `CR0.PG` and `CR4.PAE`) are set, and then loads a null IDT and executes
  `ud2`. With no IDT the `#UD` is a triple fault; the boot test runs QEMU with
  `-no-reboot` and asserts the greeting and `long mode on` came out of the
  serial port before the machine reset.

`examples/kernel0-x86_64-idt/` is the third boot: it builds the IDT, resumes
from a `ud2` and a divide by zero, takes five timer interrupts and ends in a
store through a page the stub's identity map does not cover, whose `#PF`
handler prints and halts. `plan/x86-idt.md` is its design note.

## Kernel stage 22: the IDT, the exceptions and the timer

`plan/x86-idt.md` owns the design. In short: a `static mut [IdtEntry; 256]` of
`repr(c)` 16-byte gates, five of them filled at boot from
`Ptr.from_fn(gate).addr()` (`#DE` 0, `#UD` 6, `#GP` 13, `#PF` 14 and the timer's
32), with selector `0x08` read out of this stub's own GDT, IST 0 and a `0x8E`
interrupt gate; `lidt` takes a separate packed ten-byte descriptor. A gate is a
naked function that builds a `repr(c) TrapFrame` on the interrupted stack (the
CPU pushed `RIP`, `CS` and `RFLAGS`, and an error code for 13 and 14; the gates
for the rest push a zero so one frame layout serves every vector), calls a Kelp
`trap_dispatch(frame)` through the GS base, and returns with `iretq`. The
8259 pair is remapped to vectors 32..47 and only IRQ0 is unmasked; PIT channel 0
is programmed for about 100 Hz through ports 0x43/0x40. No compiler change was
needed: `Ptr.from_fn`, `naked fun`, `asm` operands, `align(N)` and the static
array of a `datac` were all in place, and the one thing the stage had to solve
in the language was reading the dispatcher's address without clobbering an
interrupted register (an `asm` operand is materialised before the gate saves
anything, so the gate reads it from the GS base instead).

## What is not here

The APIC (local and I/O), SMP, ACPI, a TSS and an IST stack, `syscall`/`sysret`,
x86 user mode, and the SSE/XMM state in the trap frame: the gates save the
general registers only, which is honest for a kernel whose own code does not
keep live `xmm` values across a fault. The `interrupt`/calling-convention
attributes stage 5 deferred are still open. `cpu_index()` has no x86-64
lowering yet, so a `percpu` static is refused by name for this triple. There is
no second x86-64 boot path (a Multiboot 1 header): SeaBIOS' PVH support accepts
the ELF64 image on this machine's QEMU, so the fallback was never needed and is
not carried.
