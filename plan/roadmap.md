- **Shipped by MK5-S2-M1, and the shape it took**: `io` is **ungated** (open item 38 answered: writing your own stdout and reading your own stdin is authority over nothing shared, so no `io` domain exists yet) and is one `File` over a file descriptor a file, a pipe, a socket and a terminal are the same thing at the POSIX level, so there is no reader/writer hierarchy and no traits to build one from. The surface is `read`/`read_into`/`read_all`/`write`/`write_text`/`write_str`/`close`/`flush`/`set_nonblocking`/`wait_readable`/`wait_writable`, the three standard descriptors, `Line` with `io.read_line`/`read_lines`/`io.read_all`, the builtin `print`/`print!` under explicit names plus `eprint`/`eprint_bare`, and an owned `BufReader` datac with `read_line_into`/`read_line`/`read_all` (open item 49 answered: yes, a `datac`, with the one process-wide reader over stdin held in a module-scoped `pd var`). `process` is gated on `process` and ships `run`/`spawn`/`Child.wait`/`kill`/`is_running`, `args`/`arg_count`, `exit`/`getpid`. The grant names the **program** as its own argument never `argv[0]`-by-convention so `process = ["/bin/sh"]` is one absolute path checked before the fork; like `fs` (and unlike `net`'s planned vocabulary) the check resolves symlinks first, which on a NixOS machine means the grant names the resolved `/nix/store` tree rather than the `/bin/sh` link the caller wrote. argv needed the one compiler change MK5-S2-M1 predicted (open item 50): the emitted `main` is now `int main(int argc, char** argv)`, saving both into two runtime globals that only `std/process` reads. **MK5-S2-M2** then added the per-call working directory (`spawn_in`/`run_in` with a `chdir` in the child, code 126 when the child cannot enter it) and the fallible `try_run`/`try_run_in` returning `Result<RunResult, ProcErr>`.
- **Shipped by MK5-S3, and the shape it took**: the `net` vocabulary is `host`, `host:port`, `*.host`, `*:port`, `*` validated in one place (`resolve.rs::validate_net_pattern`), matched by a matcher of its own (`codegen_c`'s `kelp_host_glob`/`kelp_host_match`), with `*` matching within one label and a lone `*` the whole-resource wildcard the entry module holds. The split is at the *last* `:`, which is also why an IPv6 literal is unexpressible as a pattern rather than ambiguous. `checked_args` became a `Vec<CapCheck>` instead of a `Vec<usize>`, because for `net` *which* arguments are resources is a property of the call rather than of the argument types: `net.send_text(s, text)` has a `str` argument that is not a resource, and `net.recv(s, max)` a `usize` that is not a port. `connect` checks host and port together; `listen` checks the port alone, because a listener binds the machine and v1 has no `net.listen(host, port)` so for a listener the port *is* the resource, and a pattern with no port constrains none; `resolve` checks the host alone, ignoring the pattern's port, because resolution is not port-specific. The module is `connect`/`listen`/`accept`/`send`/`send_all`/`send_text`/`recv`/`recv_into`/`close`/`Listener.close`/`shutdown_write` plus `Listener.port`/`Socket.peer_addr`/`Socket.wait_readable`/`Socket.wait_writable`/`Socket.set_timeout`/`net.resolve`, on top of thirteen `extern` bodies with `MSG_NOSIGNAL` on every `send`, so a peer that closed cannot kill the process with `SIGPIPE`, and `EAGAIN` reported as "timed out" rather than "receive failed". `net.resolve` returns `List<String>` (addresses formatted with `inet_ntop`, deduplicated in resolver order), not a `getaddrinfo` blob.

- **Three latent bugs MK5-S2-M1 flushed out, all earlier than MK5-S2-M1, all now pinned by the suite**: an empty `Bytes`/`String` used to hold a NULL `data`, so `Bytes.empty().as_str()` and any `print` of an empty owned buffer handed NULL to `strlen`/`printf`. AddressSanitizer caught it on the first `io.read_all()` of an empty stream, because the ASAN pass gives the child no stdin; the two empty constructors now allocate the single NUL byte the invariant always claimed (`data[len] == 0`, including `len == 0`). A `File` write goes straight to the descriptor with `write(2)` while the builtin `print` and templates go through stdio's buffer, so the write primitives now flush the matching stdio stream first (`kelp_io_flush_stdio`) without that, `print("a")` followed by `File.write_str("direct")` came out `directa` whenever stdout was a pipe, which is exactly what the io fixture showed before the fix. And a module holding a domain with an **empty** pattern list (`with caps(process = [])`) emitted no allowlist at all, so any call that names a resource referred to a symbol that was never defined and `cc` rejected the program; the empty list is now emitted as `{ NULL }` and denies, which is what makes an empty grant a usable thing to hand out. One borrow-checker consequence worth knowing: a `Line`'s text cannot be moved out of it (v1 has no partial moves), so the owning form is `BufReader.read_line_into(out)`, and a `RunResult` moves as a whole rather than field by field.
- **Partly unblocked, still missing**: appending to a *file* shipped in MK4-S1-M1, owned buffers grow in memory (`String.push`/`push_str`/`reserve`/`clear`/`with_capacity`, `Bytes.push`/`append`/`reserve`/`clear`), and the `List` ordering surface shipped in MK5-S1-M4 `index_of` is the only piece of it still unwritten, deliberately deferred to MK5-S6-M1 (open item 42) rather than shipping a `-1` sentinel. `env`'s real bodies, `Map`, and the filesystem breadth (`fs.mkdir_all`, `fs.remove_all`, `fs.walk`, `fs.copy`, `fs.open`, `fs.metadata`, `fs.temp_path`) shipped in **MK5-S5**; the HTTP client shipped in **MK5-S4** (keep-alive, framing, the pool, redirects) with `https` still out, because TLS is MK5-S4b-M1 and a dependency decision; `Option`/`Result` is MK5-S6-M1. Two limits MK5-S2-M1 records as deliberate rather than accidental: `process.run` **buffers both output streams whole** (there is no streaming capture form, so a child with unbounded output wants `spawn` instead), and there is **no process-wide `chdir`** a global working directory would make every grant pattern's meaning depend on mutable global state. MK5-S2-M2 answered the second without weakening it: `spawn_in`/`run_in` `chdir` in the *child* only, and added `fs.symlink` to the filesystem breadth (both paths checked), the fallible `try_run`/`try_run_in`, and `process.executable`.
- **Backlog, not scheduled: Coral (open item 72)**, the project-layer build tool and package manager. `kelpc build` compiles one file or one directory; this repo already carries shell scripts and test-harness code that a build tool should own (`bench/speed/run.sh`, the flag logic in `kelpc/tests/compile_and_run.rs`, the build command in `examples/download.kp`'s header comment). Coral owns the manifest, the task graph, dependencies, caching and artifacts, and leaves compilation to `kelpc`. An earlier revision made this MK13 with six stages; it is an open item now, and the design sketch is in the Backlog part below. Coral is not next: nothing in MK5-MK11 depends on it, and `cargo test` plus `bench/speed/run.sh` own the build today. Writing the parts of Coral that shell out against this stdlib turned up **three stdlib-sized gaps** (`process.spawn_in`, a fallible `process.run`, `fs.symlink`), all three shipped as **MK5-S2-M2** plus MK5-S5's continuation, and one that closed itself when captures shipped — all four are in that section's "What the port hit". None of them was a language feature, and none is left: what a port still needs is the compiler's CLI contract (open item 72), not the stdlib.
- **Far future, and wanted**: MK7 the language's **own backend**, so `kelpc` emits machine code instead of C. The measured case for it is compile time (~95% of `kelpc build` is the C toolchain's fixed overhead, not Kelp's compiler) and the measured cost is runtime (`-O0` vs `-O2`, 1.2–5.4x on the `bench/speed` workloads). It is on the list because "my own language, not C with a mask" is a project goal in its own right, not because it would make Kelp faster. MK7 is not the end of the far-future list, though: the language surface needed to write `kelpc` itself in Kelp, and the substrate needed for deep systems work (kernels, drivers, firmware, allocators), are each recorded in the Backlog part below. Nothing there is scheduled, and none of it is v1 or v1.1 work. What stays in this file is the three structural blockers and the three reversals those lists contain (see **Far future additions** below).
- **Deferred despite being in `syntax.md`'s deltas**: `caps(...)` is the last one. Those deltas were aspirational scheduling and lost to implementation order; the milestone list below records where each one is now targeted (`impl` imports shipped as MK2-S1-M1, `pd` and templates as MK2-S1-M2, `alias` substitution as MK2-S1-M3, `caps(...)` at MK4-S1-M1).
- **The heap exists, and ownership is checkable at runtime.** `Bytes` and `String` are non-`Copy`, so assigning or returning one moves it; it is freed at the end of the block that owns it, and a `datac` with an owned field drops its fields recursively. A passdown of an owned type is freed by an `atexit` handler, which is v1's only drop point at process exit. The suite proves all of that rather than asserting it: every heap fixture is rebuilt with `-fsanitize=address` and run, so a double free, a use-after-free, or a leak fails `cargo test`. That caught two real bugs during MK3-S1-M1 (a branch merge that dropped the drop candidates, and a reassignment that leaked) which is the point of the milestone.
- **A growable sequence type exists, and it is a compiler builtin, not a user generic.** `List<T>` holds scalars, `String`, `Bytes` or a `datac`; a borrow or a `str` view cannot be an element (an element outlives the list, and v1 has no lifetime syntax to say otherwise), and neither can another `List`. It is non-`Copy`, so MK1-S3-M1's move checking and MK3's drop plan apply unchanged: `push` moves an element in, `pop` moves one out, and the list frees its elements and then its buffer at the end of the owning scope in a `datac` field and an owned `pd` too, through the same `needs_drop` hook `Bytes`/`String` use. `get` returns a copy for a `Copy` element and a borrow for an owned one. Codegen is monomorphized: one C struct and one function set per element type the program mentions, emitted (for a `datac` element) together with that struct. Element types are part of the type, so `List<i32>` and `List<String>` are different C types with different functions the price is that a `List` cannot be passed to a function that does not name its element type, which is what a real generic would fix.
- **A type can now refer to itself.** `Box<T>` (MK3-S2-M2) is the second builtin container: one heap cell holding a value or nothing (`Box.empty()`), with `of`/`get`/`set`/`take`/`is_empty`. Its empty state is what makes a recursive `datac` expressible without `Option`, and both containers are pointer-indirect so `datac Node(val next: Box<Node>)` (a linked list) and `datac Tree(val kids: List<Tree>)` (a tree) both work, as does a mutually recursive pair. A `datac` naming itself or a later `datac` **by value** is still refused, with the fix in the message.
- **One emission order, and it is what makes recursion work.** Container typedefs are emitted *before* every `datac`, holding their contents through a pointer and naming a `datac` element by a forward-declared struct tag; struct typedefs are tagged for exactly that; container *functions* are emitted after the structs, innermost instantiation first, with drop prototypes ahead of them so a `datac` that owns a container can call one. That ordering is also why the recursive drop (`Box<Node>` whose pointee owns a `Box<Node>`) is correct rather than a double free ASAN proves it on a 200-node list.
- **The stdlib is no longer hypothetical.** `kelpc/std/` ships fifteen modules inside the compiler binary (`stdlib.rs`, `include_str!`), all written in Kelp and reachable as `impl "std/fs"` etc.: `mem`, `str`, `path`, `math`, `fmt`, `io` (ungated), `fs`, `time`, `rand`, `env`, `process`, `net`, `option` and `result` (all four ungated — `http` is ungated and holds `net`, delegated by its importer). The only non-Kelp pieces are `extern fun` bodies supplied by `externs.rs` allocation, `strlen`, the `&str` primitives, the float-format and `strtoll`/`strtoull`/`strtod` conversions, the libm calls, and the syscalls behind `fs`/`io`/`process`/`net`/`time`/`rand` plus `env`'s three stub panics. That is stdlib decision 3 in practice: the policy is Kelp source, the unportable primitive is C.
- **Capabilities are real, and the gate is compile-time.** A module's capability set is received from its importer (the entry module holds everything), a delegation must be covered by what the delegator holds, and referencing an ungranted namespace is a *resolution* error `fs.read` does not resolve, rather than resolving and being rejected at runtime. The runtime check that does exist is the fine-grained one: each call site's path or name argument is matched against the *calling module's* compiled-in allowlist, after lexical normalization and symlink resolution, in that order. `caps_denied` (a path outside the grant) and `caps_symlink` (a link inside the grant pointing outside it) both panic with the `.kp` call site, the attempted path, and the granted patterns.
- **Alias substitution is textual, and that shows.** `%*name*%` is spliced in as raw text before parsing, so `%*doubled*% = %*answer*% * 2` with `%*answer*% = 40 + 2` prints 44, not 84 precedence is whatever the expansion produces. That is the accepted cost of the plan's "pretty simple" choice over a hygienic macro system; `kelpc/tests/fixtures/aliases.kp` pins it so the behavior is documented rather than discovered.
- **`pd var` semantics, resolved and shipped** (was `syntax.md` §9's open question): a `pd var` is **read-only inside functions**. It may only be assigned at its own top-level declaration, since v1 has no top-level statement form beyond `pd` itself. Functions that reference a passdown receive it as a **shared borrow** (for non-`Copy` values) or by value (for `Copy` ones), so no function can write through it and no cross-function exclusivity rule is needed. `syntax.md` §9's list of options is answered by that sentence; the syntax authority is unchanged (semantics are the plan's call, not the syntax file's). Implemented in MK2-S1-M2.
- **Passdown visibility is module-scoped.** This was not specified anywhere; MK2-S1-M2 answers it the way MK2-S1-M1 answered imports only functions in the module that declares a passdown can name it, and there is no `alias.name` spelling for another module's passdown. Recorded as an open item below, since it is a v1 restriction rather than a considered design.
- **Not shipped, and known**: every function whose result is a *view* of something that would have to be truncated (`path.parent` and `path.stem` return an owned `String` instead). `env`'s bodies and the fs breadth (`fs.mkdir_all`, `fs.remove_all`, `fs.walk`, `fs.copy`, `fs.touch`, `fs.open`, `fs.read_lines`, `fs.temp_path`, `fs.metadata`) shipped in **MK5-S5**, and `Map` with them. *N* items are no longer on that list: `fs.list` and `str.split` return `List<String>` as of MK3-S2-M1. Buffer growth is no longer on it either: MK5-S1 shipped `String.push`/`push_str`/`reserve`/`with_capacity`/`clear`, `Bytes.push`/`append`/`reserve`/`clear`, `str.concat`, `panic`/`assert`, integer conversions, the number/parse/`fmt` surface, and the `List` ordering methods.
- **Known doc bug, not a compiler bug**: `syntax.md`'s (and the plan's) own "Full example" mutates a `val` field (`datac Circle(val r: f64)` then `fun mut Circle.grow(by: f64) { r += by }`), which directly contradicts the `Counter` example's own stated rule just above it ("no binding mutability can fix" a `val` field). The compiler correctly rejects this `kelpc/tests/fixtures/receiver_methods.kp` uses `var r: f64` instead. Left un-edited in `syntax.md` itself since that file is locked as the syntax authority and nobody asked for that edit; flagging it here so it doesn't get "fixed" by loosening the compiler instead.
- **Also deliberately left as-is in `syntax.md`**: §8's `impl "logger" with caps(fs = ["/var/log/myapp/*"])` and §11's full example both use `with caps(...)`, which the parser rejects with an explicit "not implemented until MK4-S1-M1" message (MK2-S1-M1 lexes `[`/`]` for exactly this). `caps` is scheduled, not dropped.

## Milestone naming

Every tracked unit in this plan carries an MK/S/M identifier.

### Hierarchy

| Level | Prefix | Scope | Meaning |
| --- | --- | --- | --- |
| **Mark** | `MK` | Project-wide | A major era of the project. The largest tracked unit. |
| **Stage** | `S` | Within a Mark | A significant sub-project within a Mark. |
| **Milestone** | `M` | Within a Stage | The smallest tracked unit. |

Read as MK > S > M.

### Identifier format

- **Mark**: `MK1`, `MK2`, `MK3`, … numbered continuously across the project.
- **Stage**: `S1`, `S2`, `S3`, … numbered continuously within its Mark.
- **Milestone**: `M1`, `M2`, `M3`, … numbered continuously within its Stage.

A fully-qualified identifier is written `MK1-S2-M3`. In context the short form (`M3`) is sufficient.

### Rules

- **(a)** A Mark is closed when all its Stages are closed.
- **(b)** A Stage is closed when all its Milestones are closed.
- **(c)** A Mark is not renumbered once any of its Stages has shipped.
- **(d)** A Stage is not renumbered once any of its Milestones has shipped.
- **(e)** New Milestones append within their Stage; they are not inserted between shipped Milestones.
- **(f)** Backlog items keep their `A-n`/`B-n`/`C-n`/`D-n`/`E-n` labels until an item is promoted to a Stage. The items themselves live in the Backlog part below.

### MK5-S5 maps, fs/OS breadth, and the real `env` (DONE)

*Deliverable*: a keyed container, the filesystem functions that are cheap now that `List` exists, and `env` bodies that are not stubs. *Gate*: none for `Map`; `fs`; `env`.

*Shipped, and what it cost*: three commits. **`Map<V>`** (part 1) is the second builtin generic, and the sketch's shape held: `String` keys, a monomorphized value type, FNV-1a over the key's bytes, open addressing with tombstones. The one design choice worth recording is that entries live in a **dense insertion-ordered array** and the hash table is a separate index of `entry index + 1` (`0` empty, `SIZE_MAX` tombstone), because `keys()` must return insertion order; a removal marks the entry dead and tombstones its index slot instead of shifting, so the order is stable. The value is held through a pointer, which is what lets the map typedef still be emitted before every `datac`. **Its key type became generic in A-2** (`Map<K, V>`, with `Map<V>` kept as the `String`-key shorthand), which turned the two `String`-specific hash/equality helpers into per-instantiation ones generated from the key type. `get` borrows an owned value and copies a `Copy` one; `get_or` and `values` are offered only for a clonable value type, exactly as `List.slice` is. **fs breadth and path polish** (part 2) are ordinary Kelp over six new externs; the two interesting ones are `mkdir_all`, which is one recursive C extern precisely so the grant is checked once on the whole path rather than once per prefix *above* the granted root, and `copy` (one `sendfile` loop). **`fs.symlink`** arrived afterwards, as the continuation MK5-S2-M2's `done.md` entry records: both of its paths are checked, which keeps an `fs` grant closed under link creation. **`env`** (part 3) replaced the three stub externs with four real ones (`getenv`/`setenv`/`unsetenv`), added the `unset` the sketch had but the stub module never declared, and proved the check is on the *name*, before the call: a grant on `PATH` does not let the holder ask whether `HOME` exists.

*Two capability-matcher gaps this milestone flushed out, both earlier code, both now pinned*: `fs.open`'s second argument is a **mode string** (`"r"`/`"w"`/`"a"`/`"rw"`), and the `fs` domain matched *every* `str` argument as a path so the mode would have been normalized and denied. `fs` now names its resource arguments per call, the shape `net` already used. And a trailing `/**` did not admit the **directory itself**, only paths below it, so a grant on a tree could not create or remove the tree's own root which is exactly what `mkdir_all` and `remove_all` do. `kelp_glob_match` now treats a trailing `/**` as zero or more segments, so `/var/lib/app/**` covers `/var/lib/app`. Both were invisible while the entry module holds the whole-resource wildcard, and both only show up in a delegated module or a fresh `mkdir_all`.

*What is not shipped, deliberately*: `Map.of` (a map starts empty) and `Set` (`Map<bool>` covers it open item 41); `env.names()` (listing is reading all of it); `fs.copy` on a directory; and `path.stem` is owned rather than `&str` as the sketch wrote it, because a prefix cannot be a view without a length-carrying view type (open item 44).


*Cost and notes*: `Map` is the second builtin generic and deliberately the cheap one `String` keys, monomorphized value type, FNV-1a over the key's bytes in the runtime, open addressing with tombstones: a `Ty::Map`, a `map_sig` next to `list_sig`, a `write_map` next to `write_list`, a `Map#` arm in the call-naming switch, and a drop that frees each key, then each value if it needs it, then the table. `Map<Map<i32>>`/`Map<List<i32>>` are as impossible as `List<List<i32>>`, by the same element check. `env.names()` is deliberately absent: listing the environment is reading *all* of it, which a grant of `["PATH"]` should not permit (if it ever ships, it is the one function whose check is "must hold `*`"). `fs.copy` is the only place `sendfile` is genuinely better than a read/write loop a 20 GiB copy would double the memory, and the repo already benchmarks a 20 GiB write. `fs.walk` needs `path.join` per entry (20 lines of Kelp, inheriting `fs.list`'s sorted order, which is what keeps the test deterministic). `fs.remove_all` is already proven in the repo: `caps_list`'s recursive `clear` does it in ~15 Kelp lines, and after MK5-S1 it is 8.

### MK5-S6-M1 `Option`/`Result` (DONE, in four commits)

**Shipped first, the cheap half** (the preparatory work, recorded in `done.md`): the error-`datac` convention is written down in `architecture.md`'s naming rules (`ok` first; a value field named for its type — `value`, `text`, `bytes`, `at`; a `message: String` when the failure is textual), and every shipped error `datac` already satisfies it, so the audit changed no code. And every syscall failure now names its cause: `kelp_panic_at`/`kelp_panic_errno` print `errno` and `strerror` on a second line below the unchanged `panic: <msg>` prefix, `kelp_panic_gai` does the same with `gai_strerror` where `getaddrinfo` is the caller, and the call sites in `externs.rs` that clean up before panicking capture `errno` first so the cleanup cannot overwrite it. Argument-validation panics and the ambiguous "short read"/"short write" cases stay on plain `kelp_panic`.

**Shipped in MK5-S6-M1**, after the three prerequisites A-3 named: tagged unions landed as MK8-S1-M1 part 1, generics as part 2, and the propagation surface (`if let`, `?`) plus the two modules and the migration are MK5-S6-M1 itself. What remains unshipped here is the machinery a *library* wants on top: `map`/`and_then` (A-4 function values, shipped as MK8-S1-M2 phase D) and any error *conversion* (A-12 traits). What it needed was exactly the three features A-3 named — a tagged-union representation, patterns that can bind and destroy a payload, and generics for it — each with parser/type/borrowck/codegen surface. **The cheap half was worth doing first** precisely as intended: with the error-`datac` field names standardized and `errno` in the panic text, the migration itself was mechanical, and it landed with the two modules as one of four phases.

### MK5-S7-M1 concurrency: what is possible now, and what is not

Deliverable: an answer, plus `poll`. What works without new language features **multi-process** (`process.spawn` is real parallelism and real isolation, and it is the honest v1 answer), **single-threaded event loops** (`poll` readiness on `File`/`Socket` + `time.sleep_ms` is enough for a server at this scale), and the existing cleanup points (`atexit` + scope drops; there is no `defer`, no cancellation, and a panic takes the process since `kelp_panic` calls `exit(1)`). What a thread would need, and why each piece is missing: a *function value* to run (no first-class functions anywhere in the parser), owned data to hand to it (open item 1: there is no move-taking parameter spelling, so a spawned thread could only borrow something whose lifetime the checker cannot relate to it), a rule about `&mut` crossing the boundary (lexical, function-local lifetimes), and a per-thread frame/cleanup story (drops are keyed to lexical blocks in one function). Conclusion: **no threads until function values *and* move-taking parameters exist** a language milestone, not a stdlib one and `async`/`await` needs those plus a state-machine transform in codegen. MK5-S7-M1 is therefore written down as "processes + `poll`" and revisited when a real program demands more.

### MK7 (far future) own backend: compile Kelp to machine code, not to C

branch takes, so stage 1 is a hand-written x86-64 backend from its first commit, not a Cranelift prototype.*

Stated as a goal in its own right: *Kelp should stop being C with a mask*. Nothing about the language's identity lives in the backend the differentiators are the capability system and the move/borrow model so this is not about making Kelp faster. It is about Kelp not depending on a C compiler to exist, and about fixing the one thing that is actually bad today: **compile time is ~95% somebody else's fixed overhead.**

#### Why (measured 2026-09-18 on this machine, best-of-5, using the C that `kelpc build` already keeps next to the binary):

| program | `kelpc build` | clang + link | Kelp's own pipeline |
| --- | --- | --- | --- |
| `examples/hello.kp` (230 lines of C) | 80 ms | 76 ms | **~3 ms** |
| `bench/speed/speed.kp` (532 lines of C) | 108 ms | 102 ms | **~4 ms** |

And inside clang's share: cc1 startup plus system-header preprocessing ~38 ms (that is the *entire* cost of `-O0 -c` on the trivial file), optimizer ~25 ms on the bigger one, link ~46 ms even for a prebuilt `.o`. So ~76–102 ms of every `kelpc build` is fixed toolchain cost, and our whole lexer → preprocess → parser → infer → borrowck → codegen pipeline is 3–4 ms. A backend that emits an object and calls `ld` directly could plausibly reach ~10 ms compiles a 10x compile-time win and no `cc` dependency.

**What it costs, measured rather than guessed:** the *same* generated C compiled `-O0` vs `-O2`, on the four `bench/speed` workloads:

| workload | `-O0` | `-O2` | penalty |
| --- | --- | --- | --- |
| `collatz` (branchy int) | 446 ms | 83 ms | 5.4x |
| `float` (div + add loop) | 265 ms | 101 ms | 2.6x |
| `mix` (div-bound loop) | 204 ms | 168 ms | 1.2x |
| `fib` (real calls) | 28.4 ms | 24.0 ms | 1.2x |

`-O0` is the worst realistic case (everything spilled, nothing inlined). A hand-written backend with a decent register allocator lands between `-O0` and `-O2`: call-heavy code barely notices, branchy and FP-heavy code notices a lot. Closing the rest of the gap means writing an optimizer inlining, CSE, LICM, strength reduction which is the multi-year part (LLVM is millions of lines; Cranelift is six figures and lands around `-O1`). **That is the trade: ~10x faster compiles and no toolchain, for ~1.5–3x runtime on numeric code until an optimizer exists.**

**Staged path** (each stage is testable with what already exists):

1. **Backend boundary.** `codegen_c.rs` becomes one implementation of a backend, `driver.rs` (43 lines, and the only place that shells out) picks one, and `kelpc build --backend=…` selects it with an env-var override so the 118 end-to-end tests, which are backend-agnostic by construction (compile, run, compare stdout), can validate both backends in one `cargo test`.
2. **Cranelift** (`cranelift-codegen` + `cranelift-frontend` + `object`) for the scalar subset first: no `Bytes`/`String`/`datac`. This is where the compile-time win lands and where the runtime gap is smallest. The `tir` surface is small enough for this to be a real option: 177 lines, ~16 node kinds, four scalar widths.
3. **`datac` layout**, calling convention, and `extern "C"` calls so the ~20 one-line externs (`sqrt`, `clock_gettime`, `stat`, …) keep working as direct calls.
4. **Move the non-trivial runtime out of C**: `externs.rs` (251 lines of C bodies) plus `PATH_RUNTIME`/`CAP_RUNTIME` (the glob matcher, the `..`-rejecting path normalizer, `realpath`-with-a-missing-tail). Two fiddly pieces to plan for: `print` currently goes through C's `printf`, and on x86-64 SysV calling a variadic function requires setting `AL` to the number of vector registers used; and the capability checker's matcher/normalizer are Kelp-visible behaviour that is currently C text.
5. **Then decide.** Keep Cranelift, hand-write x86-64 (own register allocator, no optimizer), or go all the way to a static ELF with raw syscalls and our own runtime allocator, formatter, and `fs` which is the only path to a genuinely self-contained binary.

Things that get *better* rather than worse on the way: GNU statement expressions and compound literals leave the strategy (a real backend handles value-position blocks natively), `-fwrapv` becomes explicit wrap semantics we control, and the `#line` gap (open item 20) stops being something we cannot do.

Gate it on `bench/speed/` (runtime parity, four workloads with cross-language checksums) plus a compile-time column that pair is the whole argument, and it is already in the repo.

Rejected numbering: an earlier revision of this file put moves and borrow checking at MK1-S2-M1 and retired MK1-S3-M1/MK1-S4-M1, on the theory that `syntax.md`'s deltas won. The implementation did not do that MK1-S3-M1 (moves) shipped as MK1-S3-M1 so the record above is the numbering that counts.

## Dependency notes

Mark-level edges, and the reason for each. Item-level edges are in the open items and in the Backlog part below.

- **MK9 does not depend on MK8.** An earlier revision said it did, three times, without a reason. `unsafe`, freestanding mode and user FFI do not need generics, tagged unions or `Result` to exist; the substrate is independent of the ergonomics. The ordering is a preference with one reason: the code MK9 targets (an FFI boundary with many handle kinds, a fallible call on every edge, callbacks) is where the missing ergonomics hurt most. If MK9 is ever wanted before MK8 finishes, nothing here stops it.
- **MK6-S1-M1 depends on MK9-S3-M1 (atomics, ordering, a published memory model).** This edge was implied by MK5-S7-M1 and open item 60e but never written down, and it is a real one: a thread milestone with no memory model and no atomics is not a milestone. Either MK9-S3-M1 moves in front of MK6-S1-M1, or MK6-S1-M1 ships a documented minimal atomics subset and MK9-S3-M1 completes it.
- **MK10 depends on MK4-S1-M1 (done) and MK8-S3.** Runtime-derived authority (C-1) has nowhere to live until a manifest section can restrict `main` itself (C-2, open item 18), and that section is MK8-S3's.
- **MK11 runs alongside MK9 from the first `unsafe`.** D-1 (operational semantics, an aliasing model for `&mut`) and D-2 (a UB catalogue) are preconditions for any honest claim about B-3, B-4 and B-9. They cannot wait until MK9 is finished.
- **Block E restated.** Block E calls A-7/B-7 (allocators), B-6 (freestanding) and B-4 (concurrency model) "decisions to make, not tasks to schedule". **MK9-S3, MK9-S4 and MK9-S5 are those items.** Promoting them to numbered Marks does not remove the decision; it records that the decision is to be made inside a tracked Mark rather than left in the backlog.
- **Coral and the regulated-domain question have no edges into MK5-MK11.** They are open items 71 and 72. See the Backlog part below.

## Open items

1. ~~**Move-taking parameters have no spelling.**~~ Resolved twice, in opposite directions, which is worth reading in order. **MK1-S4-M1** settled it as "no move-taking parameters in v1, by design": a `datac`-typed parameter is always a borrow (shared, or exclusive via `mut T`), and a value moves only by local rebinding. **MK8-S1-M2 phase A reverses that**: `name: move T` takes ownership, the call site moves the argument in exactly as `val b = a` does, and the callee frees it when its scope ends. `mut` and `move` are mutually exclusive; `move` on a `str`/`&T` is refused (a borrow has no owner to transfer) and so is `move` on a receiver (a method that consumed its receiver would destroy the caller's value at a call that reads like one). The type-level change is one line — the parameter resolves to the bare `T` instead of `Ty::Ref` — which is why the borrow checker and codegen needed no new rule.
2. ~~**`pd var` semantics and the `pd` wiring pass.**~~ Resolved twice: MK2-S1-M2 made a passdown read-only inside functions, and MK2-S2-M2 replaced that with a hidden *borrow* typed by the declaration (`pd var` exclusive, `pd val` shared), so a `pd var` is writable from any function that references it while every access stays borrow-checked.
3. ~~**`pd` and `Bytes`/`String`.**~~ Resolved in MK3-S1-M2. An owned passdown is allowed and its drop point at process exit is an `atexit` handler registered alongside the generated global's initializer, so `pd val banner = String.from_str("...")` works and is freed. Reading an owned passdown inside *another* passdown's initializer is still rejected ("its value is not Copy") unchanged from MK2-S1-M2, now enforced by `is_copy` rather than by naming `datac` specifically.
4. **`when` is boolean-only in v1.** *Resolved in MK8-S1-M1 (part 1)*: `when` now has both forms — no scrutinee means the boolean chain (unchanged), a scrutinee means patterns over an `enum`, with exhaustiveness checked and a missing variant named in the message. The remaining Kotlin-isms (nested/literal patterns, guards) are deliberately absent; a pattern is a variant name plus one binding per payload field, and `_` ignores one.
5. ~~**`process.run_shell`**~~ Resolved in MK5-S2-M1: no shell-shaped entry point ships. `process.run(program, args)` takes the executable and the argument list separately, which is what makes the capability check a single absolute path; a caller that wants a shell writes the shell's path itself, and the grant then says so (`process = ["/bin/sh"]`).
6. ~~**Is `io` (stdin/stdout/stderr) really ungated?**~~ Answered in MK5-S2-M1: **ungated**, which is the same answer as item 38 (that item is this question asked from the purity side). `std/io` has no `domain_of` row and `io` is not in `stdlib::DOMAINS`, so there is nothing to gate it with even if a caller writes `with caps(io = [...])` the error says `io` is not a capability domain.
7. **`math` on `f32`.** Either add `f32` overloads or accept implicit `f32 -> f64` promotion, which interacts badly with inference. With overloading locked in (stdlib decision 4), the clean answer is `f32` overloads.
8. **`String` API surface.** The standard library section in `architecture.md` sketches `String` largely in parallel with `Bytes`, and decides that text-returning `str.*` functions return `String` rather than `Bytes`. That decision is this document's, not `syntax.md`'s confirm it, especially whether `path.join`/`path.normalize` should return `String`.
9. **Canonical top-of-file order** is `impl`, then `pd`, then `datac`/`fun`, and `%*alias*%` may appear in any of those. Enforced for `impl` (MK2-S1-M1) and `pd` (MK2-S1-M2) each is a parse error after any `datac`/`fun`. MK2-S1-M3 answered the `%*alias*%` half by taking it out of the parser's hands entirely: `alias` declarations are stripped by `preprocess.rs` before the parser runs, so a declaration is legal anywhere a statement could start and the canonical order does not apply to them. References keep their slot.
10. **Passdowns are module-scoped, with no cross-module spelling.** MK2-S1-M2's answer to a question `syntax.md` §9 leaves open. If a passdown should be reachable from another module, the syntax needs a spelling (`util.shared`? a parameter?) and the wiring has to reach across the module boundary today naming another module's passdown is an error that says so.
11. **Trailing-operator line continuation is claimed by the plan, not by the compiler.** This document's style list was revised to say that a line ending in `.`, `+`, `,`, `&&`, or `=` continues onto the next line. `syntax.md` §10 says only "newline ends a statement", the MK1-S1-M1 record says continuation was never attempted (a wrapped expression must be parenthesized), and the lexer behaves the MK1-S1-M1 way. The style bullet now carries that as an explicit aspirational note instead of a claim. Decide whether the *language* should support it, and if so schedule it as its own small lexer change (`syntax.md` would need the sentence too, since it is the authority).
12. **A `datac` may only name `datac`s declared before it.** *Generalized in MK8-S1-M1 (part 1)*: the rule is now about *types* — a `datac` field or an `enum` payload may only name a type (either kind) declared before it by value, which is why the two declaration lists carry one merged order.  Not a documented rule anywhere, but it is what the declaration-order struct table means in practice, and it is now enforced with a message that says so (MK2-S1-M2's fix for struct emission order). Mutual/recursive `datac`s would need `Box`-style indirection, so this is expected to stay a v1 restriction.
13. ~~**`kelpc fmt`** is the enforcement story for the style rules, but is not scheduled.~~ **Resolved**: `kelpc fmt` ships. It is a *token-level* formatter — the lexer gained an additive trivia mode so comments survive as tokens, and it copies each token's own source slice and rewrites only the whitespace between tokens — with `FILE` to stdout, `-w` to rewrite in place and `--check` for CI. Idempotent, token-faithful and comment-preserving, and it refuses rather than guesses: a syntax error, a file whose aliases cannot be resolved, a non-regular node, or a lone carriage return used as a line terminator is reported with nothing written. Three limits are recorded in `kelpc/src/fmt.rs` rather than claimed away (prose outside its enumerated rule list is unchecked; a rule statement wrong in the same way as the pair that pins it survives; a raw-string or off-chain refusal reason is covered by no check), so this item should not be re-opened as an audit target — the remaining work is item 23's lint, not this.
14. **`syntax.md`'s milestone deltas are stale, and it still contains them.** The implemented order is MK1-S1-M1–MK3-S1-M2 done (borrowing MK1-S4-M1, receivers MK1-S4-M2, `impl` imports MK2-S1-M1, `pd` + templates MK2-S1-M2, aliases MK2-S1-M3, `Bytes` MK3-S1-M1, `String`/`extern`/stdlib MK3-S1-M2), with MK2-S2-M1 next. Either annotate that file's §12 deltas or leave it as the syntax authority only and ignore its scheduling. The precedence rule covers syntax and style, not scheduling but the file does not say that yet.
15. **Three known leaks, all deliberate, all safe.** From MK3-S1-M1: `if c { b = a }` marks `a` moved for everything after the `if` MK1-S3-M1's conservative branch merge so the branch that did not move it leaks instead of risking a double free; and an assignment through a dereferenced borrow (`*p = value`) leaks the value it overwrote, because the drop plan only records plain bindings. Added in MK3-S1-M2: assigning an owned *field* (`h.name = s`) leaks the field's old buffer for the same reason. All three are leaks, never a double free, and all three would disappear with a flow-sensitive merge plus field-granular drop tracking (a bigger change than v1 wants). A fourth candidate a non-tail statement that produces an owned value is *rejected* rather than leaked, so it is not on this list.
16. ~~**An owned buffer can only be printed from a place.**~~ Lifted in MK2-S2-M1: codegen hoists a temporary owned buffer into a C variable and drops it right after the `printf`, so `print(str.to_upper(s))` allocates once, prints, and frees. `heap_temporary_print` runs under AddressSanitizer to keep that honest.
17. ~~**`pd var` cost, and how to remove it.**~~ Resolved. Every reference to a `pd var` used to be an exclusive borrow (MK2-S2-M2), so one call could not take it both exclusively and shared. The hidden parameter's type is now decided by what the *function* does with the passdown, over the call graph: a probe pass runs with every passdown shared and records each use that needs an exclusive borrow plus every call edge, `close_pd_modes` walks the edges to a fixpoint (a caller of a writer holds the passdown exclusively too), and the pass that emits the program runs again with the result. A `pd var` no function writes is a shared borrow everywhere, so `show(cfg)` — a function that takes the passdown as an argument *and* reads it — compiles, while `combine(tally, tally)` is still refused. The edge is followed even when the callee never names the passdown, because a function that only forwards takes the global's own address: that is what keeps a shared borrow from being held across a write.

18. **The entry module is unrestricted.** `main` implicitly holds every domain with `/**`/`*`, so the grants a `main` writes on its own `impl` lines restrict the *imported* module, not `main` itself. The plan anticipated this ("until a later milestone adds a way to restrict `main` itself") and it is the reason the capability fixtures put the interesting module behind one level of delegation. The natural home for the fix is `coral.toml`: a `[caps]` section granting `main` less than everything.

19. **`env`'s real bodies.** *`io` and `process` shipped in MK5-S2-M1; `net` shipped in MK5-S3, and it was the one that needed a new idea rather than a new module host:port patterns and a socket type, which is open item 32 and is now resolved.* The gate mechanism is domain-generic and needed no change for any of them. **Resolved by MK5-S5**: `env`'s bodies are real (`getenv`/`setenv`/`unsetenv` behind four externs), `env.unset` shipped, and `caps_env` (read `HOME`, set/read/unset `KELP_ENV_PROBE`) plus `caps_env_denied` (a `PATH` grant denied a `HOME` query) pin the behaviour.

20. **`#line`-annotated C was never actually emitted.** MK1-S2-M1's record claims it shipped "as planned", and the plan's Key-implementation-notes still recommends it for debugging the generated C but `codegen_c.rs` emits no `#line` directive at all, which is why MK4-S1-M1's capability denial passes a `file:line:col` string through `diag::SourceMap` instead of using `__FILE__`/`__LINE__`. Either implement the directive per statement (the span is on every `tir` node, so it is mechanical) or drop the claim; the honest state today is that a `panic:` in the generated C names a line of *generated* C unless the caller the compiler generated passed a source location explicitly.

21. **A `String` is not a `str`.** *Half resolved in MK8-S2-M1.* The half that hurt was the other direction: a `str` (a string literal, a parameter, a slice) is now converted to an owned `String` implicitly wherever a `String` is expected — a call argument, a `datac` field, a `List` element, a `Map` key or value, a `let` with a written type, a `return`, an `if` branch, a `when` arm — so `String.from_str("...")` is no longer written at every owned site. What is **not** fixed is the direction this item was written about: an owned `String` where a `&str` is expected still needs `.as_str()`, because that conversion is a *borrow* with a lifetime rather than a copy, and an implicit one would run into the same temporary-receiver rule item 30 records. `syntax.md` §5.1 is the rule.

22. **`&str` return elision is first-parameter-only, and views cannot truncate.** *Partly resolved in MK8-S2-M1 by `View` (item 44).* Truncation is now expressible without allocating — `text.slice(a, b)` — and a `View` return follows the same elision rule, so a function can hand back a slice of its first reference parameter. The first-parameter-only limit is unchanged, and it binds a `View` return exactly as it binds an `&str` return. What is also unchanged: `path.parent`, `str.trim` and `str.prefix` still return owned values, because changing *their* signatures is stdlib work with a compatibility cost, not a language gap.

23. **User-code naming case is a configurable lint** (see "Retained Kotlin-look rules" in `syntax.md`): a numbered option, `0` = `camelCase` (default), `1` = `snake_case`, room to append more far-future, lint-only (a beauty warning, never a compile error; any case keeps compiling regardless of the configured preference). Not scheduled to a milestone. Open sub-questions for whenever a lint pass is built — item 13's formatter shipped **without** a case option, deliberately: where the setting lives (`coral.toml`? a flag?), and whether the stdlib's locked `snake_case` convention (naming decision, "Naming and style rules for the stdlib" below) stays an intentional exception or should track the configured case too.
24. **No extension methods on a builtin or imported type.** MK2-S1-M1 recorded that `fun circle.Circle.helper()` cannot be parsed (the receiver grammar takes one bare type name), and the same wall is why the stdlib plan's "receiver form is available and preferred in user code" (`name.trim()`) is not true: `fun str.trim(s: &str)` is a *free* function in `std/str`, so callers write `str.trim(s)`. `&str` return elision (MK2-S2-M1) removed the *other* blocker, so what is left is purely the extension-method spelling. Recorded here because the stdlib's own naming section promises the receiver form.
25. **`String` still is not a full peer of the plan's sketch.** `as_str` shipped in MK2-S2-M1 (as a builtin returning a view); `as_bytes` and `slice` are still missing, the first because nothing needs a `&Bytes` and the second because slicing by *length* needs the length-carrying view type of item 22. `String.char_count` counts non-continuation bytes, which is the cheap right answer but not grapheme-aware. **Equality is settled by refusal**: MK3-S1-M2 made `==`/`!=` on an owned value, a `datac`, or a `str` a type error (`compare_owned.kp`, `str_comparison.kp`), because the alternative was an invalid C `==` on two structs and for `str`, a comparison of addresses rather than text, which is silently wrong; `str.eq` is the text comparison. Byte equality for `Bytes` is still absent, and `String.concat` does not exist (whether concatenation should be an operator or `str.concat(a, b)` remains open).

26. ~~**The backend is a C compiler, and the test suite cannot yet tell.**~~ **Resolved in stage 0** (`68746a6`): `--backend=` and `KELPC_BACKEND` select a backend, an unknown name is refused by name, and `kelpc/tests/run-all-backends.sh` runs the fixture suite once per backend. The obligation this item names is now live rather than hypothetical, and the `asm` backend is where it bites: every fixture that backend builds is compared against the C backend's own binary, and the C backend stays the oracle. That is the part of the original text worth keeping — every memory-safety and capability claim in this plan was verified *through clang*, so a second backend inherits the obligation to re-verify all of it, not just the performance numbers.

27. **`List<T>` is a compiler builtin generic, and `syntax.md` did not know it existed.** *Settled.* `syntax.md` §12 documents the type and every container since MK8-S1-M1 part 2, so there is no "no collections" sentence left to fight, and the control-flow section (§6.2, which was §10 before the file was renumbered) has gained `for` as **MK8-S1-M3**. What was true while it was open is worth keeping: `List<String>` in a *type* position could never be confused with an expression, because nothing in v1 parses `<` there, and the index-and-`while` walk was only ever a scheduling statement rather than a style rule. The `for` loop desugars to exactly that walk, so the C-shaped spelling is now the compiler's, not the caller's.

28. **A list element cannot be a list, a borrow, or a `str`.** Enforced in one place (`types::is_list_element`) and explained in the diagnostic: the element is owned by the list, so it has to outlive it, and v1 has no lifetime syntax to say otherwise. A `datac` element works because its instantiation is emitted together with that struct (typedef and drop function already defined); the cost of that ordering rule is that `List<Circle>` is expressible while a *field* of `List<Circle>` inside `Circle` is not the same "a datac may only name earlier datacs" restriction as open item 12, now with a second shape.

29. **`List.get` is the one signature that depends on the element type** *and stays as it is after MK8-S2-M1*: a `View` did not make `&T` and `T` interchangeable at a use site (a `View` is a text view, not a general borrow), so the `.as_str()` chain on `List<String>.get(i)` is still there — and still removaable only by the owner-side coercion item 21 keeps open., and that leaks into ordinary code. `List<String>.get(i)` gives a `&String`, so passing it to a `str.*` function needs `.as_str()` (open item 21 compounding), while `List<i32>.get(i)` gives an `i32` and can be used in arithmetic directly. The alternative always a borrow would make index loops over `List<i32>` need a deref per element; this way round was chosen because the common cases (`print(l.get(i))`, `total += l.get(i)`) are the ones that read cleanly. Worth revisiting only if a length-carrying view type (open item 22) ever makes `&T` and `T` interchangeable at a use site.

30. **Borrow lifetimes got shorter for temporaries, and are still lexical otherwise.** *Unchanged by MK8-S2-M1, and `View` is subject to it rather than exempt*: `String.from_str("x").view()` is refused for the same reason `String.from_str("x").as_str()` is, because both hand the borrow back. A view of a *literal* (`"x".view()`) is fine, since its storage is static. Two changes came with MK3-S2-M1: a borrow produced by a *statement's* temporary is released at the end of that statement (`print(l.get(0)); l.push(x)` is now legal), and a shared borrow of a *temporary* is allowed as a call argument, with codegen hoisting it into a C variable covering the call. The line that was drawn: a call that **hands the borrow back** (`String.from_str("x").as_str()`, or `fun f(p: Pair).R: &i32 = ...`) still requires a place, because the result outlives the statement that is the case where a borrow of a temporary would dangle, and it is rejected rather than hoisted. What is *not* fixed and is worth knowing: a *bound* borrow still lives to the end of its block, so reading one element into a `val` and then mutating the list in the same block is still an error (`val first = names.get(0); names.push(...)`); the fixture wraps the read in `{ }` to show the workaround. That is the remaining cost of lexical lifetimes, and it is the same cost `view_pins_owner` records for strings.

31. ~~**`env.args`/`process.run(argv)` are now just unwritten.**~~ Resolved in MK5-S2-M1, and neither needed new compiler machinery beyond the entry point: `process.run(program, args)` takes a `List<String>` in and an exit code out, and argv is read through `process.args()`/`arg_count()` from globals the emitted `main(argc, argv)` saves (open item 50, done). `main` still takes no `.kp`-visible arguments and is still uncallable, which is the part open item 18 (the entry module's unrestricted capabilities) would have to change, not this.

32. ~~**`net`'s capability vocabulary cannot be written, and would deny every host if it could.**~~ **Resolved in MK5-S3 (part 1), as the milestone's first task and its first commit.** As found: `stdlib::patterns_are_paths` counted `net` as a path domain, so `validate_cap_pattern` rejected the `api.example.com:443` patterns the plan's own examples use, and `codegen_c` emitted `kelp_cap_check_path` for `net` which lexical-normalizes a hostname, fails, and denies everything; `checked_args("net", …)` also only ever handed over the first `str` argument, so the port was never matched at all. The fix: `net` left `patterns_are_paths`; `resolve.rs::validate_net_pattern` validates `host`, `host:port`, `*.host`, `*:port`, `*` (split at the last `:`, so an IPv6 literal is unexpressible rather than ambiguous); `codegen_c` gained `kelp_host_glob`/`kelp_host_match` and `kelp_cap_check_hostport`/`kelp_cap_check_host`/`kelp_cap_check_port`; `checked_args` became a `Vec<CapCheck>` keyed on the *call*, because `net`'s signatures mix resources with ordinary strings and numbers; and the entry module's wildcard for a name domain is `*`, which `net_loopback` pins. Two deviations from the sketch are recorded in the MK5-S3 section (`listen` checks the port alone open item 55 and `resolve` ignores the pattern's port).

33. **A borrow does not remember what it was borrowed from, so a pointer local cannot be used as a cursor.** `var cur = list` binds the borrow; `cur = cur.next.get()` is refused ("cannot assign to 'cur' while it is borrowed") because the borrow of `cur.next` is registered against **`cur`** the pointer rather than against `list`, its owner. Rebinding the *pointer* does not invalidate a borrow of the pointee, so this is over-strict rather than unsound, but it means a recursive structure is walked with a recursive function (`box_recursive.kp` does) instead of a loop, and both that walk and the recursive drop recurse on the C stack (a very deep list overflows it, as in Rust). The fix is to track provenance: a `VarState` for a reference-typed binding remembers the root its value came from, `borrow_root` follows it through `Ident`, and assignment updates it. Worth doing when a real program walks a long list iteratively; not built, because nothing needs it yet and the change touches the borrow checker's roots everywhere.

34. **User-declarable generics.** *Resolved in MK8-S1-M1 part 2.* MK3-S2-M2's own note said the milestone "wants generics, so it is where the first generic machinery gets scoped, or a monomorphic single-parameter special case is hand-rolled" the second path shipped. The cost is structural, not cosmetic: `datac Pair<A, B>`, `fun sum(xs: List<T>).R: T`, a user `Map<K, V>`, and `Option<T>`/`Result<T, E>` all need it, and the roadmap's MK5-S5 (a `Map<V>` with `String` keys, now shipped) reaches for a third builtin container rather than a user generic. That is the top of the backlog after the stdlib reaches the point where the missing feature is what blocks the next item (the roadmap's MK5-S6-M1 is exactly that decision point). **Shipped, MK8-S1-M1 part 2**: `datac` and `enum` declarations take type parameters and monomorphize on demand (`datac Pair<A, B>`, `enum Option<T>`), generic *functions* take their own (`fun sum<T>(xs: &List<T>).R: T`), a receiver method on a generic type writes the type's parameters (`fun Pair<A, B>.first().R: A`), an expression may instantiate explicitly (`Pair<i32, String>(...)`), and the builtin `Map` takes a key type (`Map<K, V>`, with `Map<V>` the `String`-key shorthand and the key set closed to `String`/integers/`bool`, because the compiler generates the key's hash and equality). Type arguments are inferred from arguments and from the expected type throughout.

35. **`panic` and `assert` do not exist, the "prelude" is not prelude, and `print` cannot show a `datac` or a `List`.** The plan's namespace section lists `print`, `print!`, `panic`, `assert` as always-in-scope builtins and `math`/`str`/`path`/`mem`/`io` as in-scope ungated namespaces; only `print`/`print!` exist, and every namespace including `std/str` needs an `impl` (the repo's own `caps_list` project shows it). Two consequences that cost real time: a program cannot deliberately fail (`panic("…")` is an undefined function, so a fixture has to reach a panic through a stdlib precondition), and a `datac` or a `List` cannot be printed at all, so every manual check of MK3-S2-M2's types goes through fields and `.get(i)`. The roadmap's MK5-S1 adds `panic`/`assert`; printing a `datac` needs either a derived `Debug` story or an explicit `fmt` (MK5-S1's `std/fmt` is the thin end of it).

36. **The three language features the stdlib roadmap runs into, in its own words.** (a) A **`for` loop**: *resolved by MK8-S1-M3* — `for x in list { }` is a parser desugar to the index-and-`while` walk, `syntax.md` §6.2 has it, and the fixture suite pins both the shape and the rejections. (b) A **length-carrying borrowed view** (`&[u8]`-shaped): the difference between a parser that copies every token and one that does not, and it also unblocks open items 22 and 29; needs a spelling agreed with `syntax.md`. (c) **`Option<T>`/`Result<T, E>`**: *resolved by MK5-S6-M1* — the cheap preparatory work (standardized error-`datac` field names, `errno` in panic messages) was done first, the migration turned out to be exactly as mechanical as intended, and every native that returned an `ok` flag now returns an `Option` or a `Result`.

37. **TLS for `https`: link the system library, or ship `http`-only?** Almost every real URL is `https`, and there is no TLS in Kelp. Linking the system library (`-lssl -lcrypto`, or a `libtls`) makes `std/tls`'s externs the only OpenSSL-touching code exactly the shape `std/math` has with libm at the cost of `driver.rs` gaining a link flag and the "no third-party deps in v1" rule becoming "none except the system's TLS". Shipping `http`-only is honest and free, and rejects `https` with a message naming the other options. Shelling out to a `curl`-shaped tool works today but moves the network capability to the *tool's* ambient authority, which quietly defeats the headline feature. **Recommendation**: ship MK5-S4 as `http`-only, treat TLS as MK5-S4b-M1, and start MK5-S4b-M1 with option 1 as the default never shell out as `http.get`'s implementation.

38. **Does `io` stay ungated?** *Answered in MK5-S2-M1: ungated.* WASI gates stdin as an input capability; the plan's classification says writing your own stdout and sleeping are not authority over anything shared. Gating stdin would make a filter need `impl "std/io" with caps(io = ["stdin"])`; not gating keeps the common case free. `std/io` therefore has no row in `stdlib::domain_of`, and `io` is not a name in `stdlib::DOMAINS` either, so `with caps(io = [...])` is rejected as "not a capability domain" rather than silently accepted. An `io` domain is worth adding only when `coral.toml [caps]` can restrict `main` itself (item 18), because that is the only case where a grant would have anything to say.

39. **Is argv `process.args()` (ungated) or `env.args()` (gated)?** *Resolved in MK5-S2-M1 as `process.args()`/`process.arg_count()` in `std/process`, and the gate needed one clarification.* This file's sketch put argv under `env`; argv is your own invocation, not authority over the shared environment, and `env.args` is dropped. It is *not* ungated, though: every free function of a gated module is gated, so naming `process.args` requires the `process` domain but a grant with an **empty** pattern list (`impl "std/process" with caps(process = [])`) is enough, and it authorizes no program at all. That is the right split: the domain admits the module, the patterns are the authority to execute, and `process.exit`/`getpid` ride along with argv. `main` is now `int main(int argc, char** argv)` and uncallable from `.kp` (open item 50, done).

40. **Is string concatenation an operator (`+`/`+=`) or a function (`str.concat`)?** `+` reads better and hides an allocation; a function makes the allocation visible and needs no syntax change. `syntax.md` §10 has no such operator, so an operator means editing `syntax.md`. **Recommendation**: `str.concat(a, b)` plus `String.push_str` in MK5-S1; revisit `+` as a deliberate syntax decision later, and never make `+=` on a `String` implicit it would be the only operator that allocates.

41. **`Set`, and `Map.get` on a missing key.** A `Set` as its own builtin is a third monomorphized generic for what `Map<K, bool>` already covers, and generic keys now exist (item 34 is resolved, so `Map<i32, bool>` is expressible); **recommendation**: no `Set` in MK5-S5, document `Map<bool>`, revisit with generics. For a missing key: panicking keeps `Map<String, Header>` lookups one line and matches `List.get`; a `has` check before every lookup is verbose, and an error datac per lookup is unusable inside an expression. **Recommendation**: `get` panics, `has` exists, `get_or(key, fallback)` covers the common case the same shape as `List.pop`. **As shipped (MK5-S5)**: exactly that, with no `Set`; `get_or` and `values` are additionally offered only for a clonable value type, since a `datac` value cannot be copied back out.

42. **`List.index_of`/'contains' return shapes.** `contains` is a bool; `index_of` returning `i64` with `-1` for absent is the sentinel convention the plan *rejected* in decision 2, but the alternative is an error datac for a one-line check. **Resolved that way in MK5-S1-M4**: `contains` shipped, `index_of` did not, and it arrives with `Option` (MK5-S6-M1). `str.index_of`'s `Match` datac stays as the worked example of doing it properly.

43. **Multiple `with caps(...)` clauses on one `impl` line.** Verified to parse: `impl "std/fs" with caps(fs = ["/tmp/**"], env = ["*"])`. **Recommendation**: document it in the capability section as legal (it is currently undocumented), since a `process.which`-shaped API and `std/http` holding `net` both want more than one domain and the alternative is a fake module boundary.

44. **A length-carrying borrowed view (`&[u8]`-shaped): v1.1 or later?** *Resolved in MK8-S2-M1*, and shipped as the recommendation's own spelling: a builtin **`View`** beside `Bytes`, with no `&` in the grammar. `s.view()` (one `strlen`) or `string.view()` (none), then `len`/`is_empty`/`get`/`slice`/`eq`/`to_string`, plus a `View` -> `String` copy where one is expected. `syntax.md` §11.5 is the reference. **One half of the item is deliberately not shipped**: a view *cannot be a field*, because v1 has no lifetime syntax to tie a field to its source (A-11), so the recommendation's "a borrow rule that lets it appear as a field" waits for that. Everything else fell out — see item 22 and A-8.

45. **`time.sleep_ms` needs a `time` grant in a library module.** The classification says sleeping is not a capability, but it lives in gated `std/time`, so a library module must hold `time` to sleep. **Recommendation**: leave it for now (it is a module-boundary question, not a semantics one) and move `sleep_ms`/`now_*` into an ungated module only when a real program complains the same treatment item 17 gave `pd var`'s cost.

46. ~~**Is a `for` loop worth its own milestone?**~~ **Yes, and it shipped as MK8-S1-M3**: one single-purpose commit, desugared in the parser, with the desugar pinned by a fixture, exactly as recommended. The recommendation's own ordering note — "after MK5-S1, so the first list-heavy programs show whether a loop is enough or iteration needs a real protocol (`iter`/`next`)" — is what happened: MK5-S1 through MK5-S5 were written with the index walk, and the walk turned out to be enough. The `iter`/`next` protocol stays unscheduled; it is the expensive version and nothing has asked for it. `syntax.md` §6.2 was the prerequisite and was edited first.

47. **Do panics carry errno and `strerror`?** Adding `errno` to `fs`/`net`/`process` panic messages makes every syscall failure diagnosable, at the cost of making panic text less stable for golden assertions. **Recommendation**: yes, as a two-line addition (`kelp_panic_errno(const char* msg)` used by the syscall externs), keeping the message prefix stable and the errno detail on a second line. This is also the cheap preparatory half of MK5-S6-M1. **Resolved that way in MK5-S6-M1's cheap half**: `kelp_panic_at`/`kelp_panic_errno` print `errno N: <strerror>` on a second line under the unchanged prefix, `kelp_panic_gai` covers `getaddrinfo` (whose failure is a return code, not `errno`), and a call site that cleans up before panicking captures the code first. `fs_errno` pins it; `a_failed_syscall_reports_errno_and_strerror` asserts both lines.

48. **Unicode scope.** Real case mapping and grapheme clusters need megabyte tables and a segmentation algorithm; codepoint-level handling is a table-free decode of the UTF-8 rules `kelp_utf8_valid` already implements. **Recommendation**: codepoint-level (`str.char_at`, `str.byte_index`, validated `String`), ASCII-only case operations, documented as such, no grapheme awareness and no case folding. `String.char_count` stays "non-UTF-8-continuation bytes" and the doc comment says so.

49. **Buffered IO: a `BufReader` datac, or unbuffered reads only?** *Answered in MK5-S2-M1: the `datac`, as recommended.* Unbuffered `read_line` over a pipe is one syscall per byte (unusable); buffering needs a buffer, which is an owned `Bytes` field in a `datac`. `std/io` ships `BufReader(file, buf, start, end)` with `read_line_into` as the primitive, `read_line()` as the `Line` wrapper, and `read_all()` draining the buffer first; the process-wide reader over stdin is a module-scoped `pd var`, which is what `io.read_line()`/`io.read_lines()` use, so the convenience hides the state without making it global to the user. Two limits worth knowing: `buf` must be non-empty (`read_into` reports 0 for a full buffer, which the reader reads as end of file), and an empty `Line` cannot be unwrapped by value `read_line_into` is the owning form.

50. **`main(argc, argv)` versus a `pd` global for the arguments.** *Done in MK5-S2-M1, as recommended.* A generated `pd val argv: List<String>` would avoid changing `main`'s signature, but `.kp` `main` cannot take hidden passdown parameters (MK2-S1-M2's restriction), so the runtime has to stash `argc`/`argv` either way. The emitted signature is now `int main(int argc, char** argv)`, both values are stored in runtime globals that only `std/process`'s externs read (`process.arg_count`/`arg_at`, with `process.args` built in Kelp), and no `.kp` source names them one codegen change, no new surface. A second, unplanned codegen fix came with it: function prototypes are now emitted *before* `kelp_init_pds`, because `io`'s `pd var` reader calls `buf_reader(...)` in its initializer and the init function had no prototype in scope.

51. **Should the streaming reads be primary, with the allocating form as sugar?** `net.recv(s, max)` is what people write first and cannot express "read exactly `Content-Length`" without growth; `recv_into(buf, at)` is the correct choice for a known-length body but needs a buffer the caller sized. **Recommendation**: both, with the difference spelled out in `std/net.kp`'s doc comment, and **no** `read_to_end()` until MK5-S1's growable `Bytes` exists that is precisely its use case.

52. **`process.run`'s capture model.** Whole-output capture is what people want and can deadlock on a chatty child if implemented naively (the err pipe fills while the parent blocks reading out); `poll`-based capture fixes it at the cost of a more complex extern; `spawn`-only pushes the model onto the caller. **Recommendation**: `process.run` with `poll`-based capture plus a documented "buffers both streams" memory cost, and `spawn` for the streaming case.

53. **`char` is a type with no values.** *Resolved in MK8-S2-M1*, taking the first of the two recommendations: a character literal is real. `'x'`, with `\n` `\t` `\r` `\0` `\'` `\"` `\\` and `\u{...}`; it holds one Unicode scalar value and **takes the integer type its context asks for** (so `c == '"'` works when `c` is a `u8`), which is what makes it usable in byte-level code, and it is `char` when nothing constrains it. A code point that does not fit the requested type is refused rather than truncated. `char` is a code point and not a byte, so its C type is `uint32_t`. The old text, kept for the record: `syntax.md` §5 sketches `fun push(s: mut String, ch: char)`, the primitive list names `char` (line 387), and the stdlib sketch has `str.char_at(...).R: char` in one place and `.R: u32` in another but the lexer has no char literal, no function returns a `char`, and the integer conversions of part 2a are between integer types only, so no program can produce one. MK5-S1-M1 resolved the immediate need by typing `String.push` as `u8` (the same type `str.byte` returns, and the same type `Bytes.push` takes), which is honest but leaves the padding fill in `fmt.pad_left`/`pad_right` facing the same choice. **Recommendation**: either add a char literal (`'x'`, escapes, ASCII-only) as a deliberate syntax decision with `syntax.md`'s agreement the smallest addition that makes the existing `char` type real or delete `char` from the primitive list and use `u8`/`u32` everywhere. Do not ship a third stdlib function whose parameter type no program can spell.

54. **Should integer conversions be implicit?** MK5-S1-M2 added explicit `to_<T>` conversions; the rejected alternative was implicit *widening* in arithmetic and argument matching, which would have made the conversion functions unnecessary. It was rejected because it changes arithmetic for every future program which of `i32`/`u64` wins in `i32 + u64`, whether a narrowing can ever be implicit (it must not be), and what `list.get(0) + 1` does when `get` is `usize` and because it would not have given `from_i64` its narrowing digit anyway. The conversions are 64 generated entries rather than a hand-written matrix, so the surface cost is a table. **Recommendation**: keep conversions explicit; if the ergonomics bite, the narrow fix is to let a *literal* adapt to a widening target the way it already adapts to the exact one (`f(255)` where `f(n: u64)`), not to widen operator rules.

55. **A `net` grant does not say which interface a listener binds.** `net.listen(port)` binds `0.0.0.0`; the check matches the *port* alone (MK5-S3, and see the MK5-S3 section for why the sketch's "host *and* port" was not implementable), so a module granted `127.0.0.1:8080` may listen on `0.0.0.0:8080`, which is reachable from outside the machine. That is a widening, not a bypass the module still cannot name a host or port outside its grant but it is the one place where a `net` grant means less than its text suggests. **Recommendation**: two options, in order of preference. (a) `net.listen(host, port)` with the host checked like `connect`'s, and `0.0.0.0`/`*` as the explicit "every interface" spelling honest, but it is new stdlib surface, not a fix. (b) Bind the *granted* host: the allowlist is already compiled in as constant data and `kelp_cap_check_port` already walks it, so a "give me the host to bind" accessor is possible but a pattern is a glob, so it can match several hosts and the compiler would have to pick one, which is why (a) is preferred. Not fixed in MK5-S3 because nothing needs a listener that a `*:port` grant does not already express.

56. **The pool has no idle timeout, and its ceiling is per host.** *Shipped that way in MK5-S4; item 63 records the exact semantics and the reasoning, so this item is now just the observation.* Two consequences a program can meet: it keeps `size` connections per host for its whole life (so talking to many hosts can walk into the fd limit), and a connection the peer has closed sits idle until it is used, where it fails **once**. A reaper needs a clock, which would make `std/http` hold `time` as a second capability (legal open item 43 but a policy decision). **Recommendation**: add `Pool.close_idle(after_ms)` when a real program hits either limit; do not build it speculatively.

57. **`coral.toml` gains its first numeric value, and still has no sections.** MK5-S4 introduces `http_pool = 4` (a bare integer; today the parser accepts only double-quoted strings), and rejects `[sections]` outright. The next thing that wants one is `[caps]` (open item 18, restricting `main` itself), and `http_pool` will look arbitrary sitting flat beside it. **Recommendation**: keep flat keys for one more value if possible; when the second or third numeric key arrives, add `[section]` support in one go (`[http] pool = 4`, `[caps] net = [...]`) and migrate the flat key with a clear message, rather than growing a flat namespace of deployment settings.

58. **`Transfer-Encoding: chunked` shipped in MK5-S4, not deferred.** The earlier plan deferred it and made it an explicit panic, on the grounds that a to-EOF read works for a one-shot request. Keep-alive removes that escape hatch: with a persistent connection, a chunked body has no other end marker, and reading to EOF would block until the server closed which it will not do. So the decoder ships with keep-alive. It also needs hex parsing, which `str` does not have (its `parse_u64` is decimal), so the size line is decoded byte by byte.

59. **A loopback server in the harness is now required.** MK5-S3's fixtures could be both ends in one process because `net` calls do not block on one another; an HTTP client blocks inside `send` until the response arrives, so a `Pool` cannot be exercised single-process. The helper binds `127.0.0.1:0`, passes the port through argv, and serves canned bytes and it can assert *how many connections were accepted*, which is what makes "the pool reused the socket" a direct assertion rather than a timing inference. This reverses the earlier claim that MK5-S4 needed no server helper.

60. **Threads (MK6-S1-M1): every prerequisite in one place, and the narrow shape recommended.** *(a) and (b) are shipped, as MK8-S1-M2 phases A-F: `name: move T` takes ownership, a declared function, a `fun` literal or a capturing closure is a value, and a call through one is positional with the callee's own parameter list — so a thread entry point can be a closure carrying what it runs on, which is the shape this item had ruled out as too expensive when it was written. What is left is (c)-(e) — the panic policy, the per-thread frame/cleanup story, and atomics plus a `Send`-shaped rule.)* Threads are a language milestone, not stdlib work, and they need: (a) **function values** the parser has no first-class functions at all, so there is nothing to name as an entry point; (b) a **move-taking parameter spelling** (open item 1: a `datac`-typed parameter is always a borrow, so a thread could not own what it runs on); (c) a **per-thread failure policy** `kelp_panic` calls `exit(1)`, which would let one worker's panic kill every other download; (d) a **per-thread frame and cleanup story** drops are keyed to lexical blocks inside one function's frame; (e) **atomics and a `Mutex`** in the stdlib, plus a **`Send`-shaped rule** in the borrow checker, because the model's core promise (a `&mut` is exclusive) is what a second thread would otherwise break silently. **Recommended narrow shape**, to keep the milestone as small as it can honestly be: function *references* (`thread.spawn(worker, job)` naming a declared `fun`), restricted to a single move-taking parameter enough for a worker pool, and *not* closures, which would drag in capture analysis and lifetimes. Async/`await` stays out of scope until function values exist for other reasons.

61. **`http.get` does not use a pool, deliberately.** The one-liner is `Client.send` over a fresh connection; pooling is opt-in through an explicit `Pool`. The transparent alternative would need a process-wide pool in `std/http` (`pd var`), and that is exactly what MK6-S1-M1 makes expensive: a global pool shared by threads needs a lock, and a lock around every request serializes the very thing MK6-S2-M1 is for. Per-thread pools (each thread its own `Pool`) or an explicitly shared one behind a `Mutex` are the two shapes that survive MK6-S1-M1, and neither is expressible yet. **Recommendation**: revisit transparent pooling when MK6-S1-M1 lands, and pick then do not bake a global in now and pay for it at MK6-S2-M1.

62. **`Response.header` returns an owned `String`, not `&str`.** Forced, not chosen: `&str` return elision roots at a parameter or a local, so a borrow reached through `List.get` cannot be handed back (`return headers.get(i).value.as_str()` fails the place rule, and binding the element first makes *that binding* the root instead of `self`). One allocation per lookup until a length-carrying view (open item 44) or real lifetimes make the borrow expressible. `has_header` exists so the common "is it there" question allocates nothing.

63. **The pool as shipped: `size` is a ceiling on what is *kept*, and there is no handle and no reaper.** Three deviations from the sketch, each deliberate. (a) `Lease` carries `fd`/`reused` and the pool owns the descriptors a `Lease` that owned a `Socket` could never be taken apart, since a parameter is a borrow and there are no partial moves, so `release` could not move the socket back (see item 62's rule for the general shape). The ownership story that matters is unchanged: `release` consumes the lease. (b) `size` is *max idle*, Go's reading: a request that arrives while every kept connection is busy gets a fresh one, so `checkout` has no failure path and a program never fails because its pool was small. (c) No idle reaping, so a program talking to many hosts keeps `size` connections per host until it exits reaching for a reaper means a clock, which means `std/http` holds `time` as a second capability (legal, open item 43, but a policy decision). **Recommendation**: leave all three; add `Pool.close_idle(after_ms)` when a real program hits the fd limit, and note that a stale connection is discovered on use and fails *once* (the body-framing verdict is what decides reuse, so a peer's silent close is a parse error, not a corruption).

64. **The escape set is now closed: `\n`, `\t`, `\r`, `\"`, `\\` and nothing else.** Anything else is a diagnostic rather than the bare character, which is the behavior change worth knowing about, because the old fallback made `"\q"` mean `"q"`. `\0` stays rejected for a second reason (a `str` is NUL-terminated and could not hold one). Not present and not needed yet: `\xNN` (a hex escape that runs on: `\x0d` followed by `a` is one escape in C, so it needs the same three-digit discipline `codegen_c` now uses for octal) and `\u{...}` (needs a decision about whether a `str` literal can name a codepoint directly). **Recommendation**: add `\xNN` only when a byte-level literal is genuinely awkward to write; the ASCII escapes cover every protocol Kelp currently speaks.

65. **A capability pattern is source text, so the harness and the program must agree on a literal path.** `caps_scratch` in `kelpc/tests/compile_and_run.rs` now builds `/tmp/kelp_caps_<name>` literally instead of asking `std::env::temp_dir()`: the fixtures grant `/tmp/kelp_caps_<name>/**`, and a `TMPDIR` pointing at a sandbox left the harness creating one directory while the program read another. The general rule (also worth applying to any future scratch fixture): when a test's grant is written in the fixture, the harness's scratch root is not configurable.

66. **The manifest format change Coral needs.** Today `coral.toml` is flat, holds four keys (`name`, `version`, `entry`, `http_pool`), rejects any line starting with `[`, and rejects an unknown key by name. Coral needs sections (`[package]`, `[tasks]`, later `[deps]`). Options: (a) one manifest, with `kelpc` reading the keys it knows and ignoring other sections; (b) two files, `coral.toml` for the build tool and `kelp.toml` for the project. (The rename folded the old contrast — the compiler's `x.toml` versus Coral's proposed `coral.toml` — onto a single name, so option (b) now needs a second name, and `kelp.toml` is the free one.) **Recommendation**: (a), because a project has one identity and splitting it lets the two files disagree; it also fixes the current behavior where a new compiler key breaks an old manifest. Whatever is chosen needs a stated rule for unknown keys and a way to say "this manifest needs a newer tool".
67. **What Coral is written in, and when it is ported.** Coral is a Rust program while the compiler is, which means the build tool cannot build itself and its own tasks need a compiler that exists. Writing Coral in Kelp needs MK8-S1/S2 (generics, `Option`/`Result`, function values, containers) and the stdlib breadth MK5 delivers. **Recommendation**: Rust through MK13-S4, then port as the first non-compiler self-hosting exercise, since Coral is a large real program with no unsafe requirements. (The `MK13-...` names in items 67-70 are the identifiers the Coral design carries in the Backlog part below now that it is not a Mark; open item 72 is the scheduling question.) All the language prerequisites are shipped: generics (A-2), `Option`/`Result` (MK5-S6-M1), containers (MK3), and function values with captures (MK8-S1-M2 phases A-F). What a port hits instead was three stdlib primitives — `process.spawn_in`, a fallible `process.run`, `fs.symlink` — all three shipped as **MK5-S2-M2**, so the stdlib half of this item is met as well; the remaining half is the port itself.
68. **Is a package registry acceptable?** The plan lists a package registry and third-party dependencies as deliberate non-goals, and Coral is a package manager. MK13-S3-M3 is the decision point, and MK13-S3-M1 (path and git dependencies) is worth building either way, because it pays off with no index and no trust model. **Recommendation**: path and git dependencies, and no index until a second project outside this repository needs to consume Kelp code. **Settled (`coral v0.5.1`-`v0.5.4`)**: git dependencies shipped, folders included, and the lockfile was dropped rather than written — see item 69.
69. **What a version constraint means for Kelp.** A semver range needs a compatibility theory (what counts as a breaking change in a language with no traits and no visibility rules yet), and a lockfile needs a format with a checksum story. Nothing here is decided in v1. **Settled**: nothing is versioned. A dependency is a git remote or a folder inside one; `coral sync` takes its tip and `coral build` leaves a fetched tree alone, so a lock would pin what the checkout already records and nothing more. Ranges stay open until MK13-S4-M1 makes a multi-package workspace concrete.
70. **How much authority Coral itself holds.** The Coral design in the Backlog part below gives each task its own grants and Coral none, but Coral still writes `build/`, reads sources and runs the linker, so it holds a grant set whether or not the manifest says so. The open question is whether that set is fixed and documented (build inputs, build output, toolchain binaries) or declared per project. Related: a task's output becoming another task's input without the second task holding a write grant on the first's tree. **Recommendation**: a fixed, documented grant set for the tool itself, orthogonal to per-task grants, with the C-1 runtime-authority work (MK10-S2-M1) as the thing that makes it checkable rather than documented.

71. **Should Kelp target regulated and financial domains?** An earlier revision made this MK12, with six stages (decimal arithmetic, transactional primitives, audit and traceability, formal tooling built on MK11, legacy interop, certification), and then said in the same breath that it "is a **decision to make**, not a task to schedule". A decision does not need six stages. The plan rejects an ecosystem as a goal (no registry, no third-party dependencies in v1) and has no certification section, and banking is largely an integration domain, so several of those stages run against v1's deliberate non-goals. **Recommendation**: keep it a question. If the answer is yes, the stages are in the Backlog part below and the domain gets a Mark when a real program needs it; until then nothing in MK5-MK11 changes.

72. **Coral: the project-layer build tool and package manager - a Mark, or a question?** An earlier revision made this MK13, with six stages. The design survived the review: tasks are Kelp programs with their own `impl` grants, `coral.toml` grows sections, the task graph is Gradle-shaped, and the build cache is the point. The *scheduling* did not. Nothing in MK5-MK11 depends on Coral; `kelpc build`, `cargo test` and `bench/speed/run.sh` work today; the first thing Coral needs from the compiler is a stable CLI contract that does not exist yet (`kelpc version` is its first piece, added after this release); and Coral cannot itself be a Kelp program until MK8-S1/S2 ship. **Recommendation**: open item. **What exists so far** (`coral` repo, tagged `v0.3.0`): `init`/`build`/`run`/`check`/`clean`, `[tasks]`, git dependencies (one repo, or one folder inside one; no versions, no lockfile), a fingerprint build cache, and toolchain management — global (`coral toolchain kelp use <ver>`, the `~/.coral/bin/kelpc` link) and per project (`[toolchain] kelp` in `coral.toml`, written by `coral toolchain kelp pin <ver>`), the latter being MK13-S6-M1's per-project selection, and the store under `~/.coral/toolchains/` holding one version per component since `coral` v0.5.0 — installing or using a version removes the others, so a pin that is not the stored version displaces it. The design sketch is in the Backlog part below, as is "What the port hit" — the four findings a first port produced: three stdlib-sized gaps (`process.spawn_in` for a per-call working directory, a fallible `process.run` so a missing tool is a reportable error, `fs.symlink` for the toolchain link — **all three shipped as MK5-S2-M2**) and one language gap (capture-less closures) that MK8-S1-M2 phases E-F closed. Promote Coral to a Mark when a second project outside this repository needs it, or when the compiler's CLI contract is frozen. One question has no home since `rebrand.md` was deleted (the X → Kelp rename executed; see the `rebrand/x-to-kelp` branch): what `coral`’s name replaces, given that the compiler is `kelpc` and the manifest is already `coral.toml`.
73. **A grant denial cannot be a value, so a fallible call cannot report one.** Found while shipping MK5-S2-M2's `try_run`. The capability check is compiled in per *calling* module and emitted at the call site, where it panics — so a program outside the grant, and a relative one (which normalizes to nothing), is refused before any Kelp function runs. `ProcErr` can therefore hold `NotFound`, `NotExecutable` and `DirNotFound`, all decided by a `stat`/`access` pre-check before the fork, but not the `Denied` variant the Backlog part below's row sketched. **The shape a fix needs**, in the order worth considering: (a) a non-panicking check mode in codegen, selected by the callee the way `checked_args` selects the resource arguments, where the guard does *not* call on deny and the verdict reaches the callee as a value — a hidden argument, since the callee's own return type is the only place the `Err` can be built; (b) the same, carrying the verdict in a runtime global the callee must consume, which is smaller but fails *open* if a callee ever forgets to consume it — which is why (a) is preferred. What is not in question is the panic's usefulness for the case it covers now: a manifest that grants the wrong program is a configuration error, and the message names the call site, the path and the granted patterns. Worth doing when a real program resolves a program path at *runtime* (the C-1 runtime-authority work, open item 18's neighbourhood) and has to recover from a denial rather than crash.

### 3. The minimal useful Kelp

If only five things could be added to make Kelp useful and functional without bending it:

1. **A length-carrying view.** The biggest single lever for text, parsers, network and paths; it closes three open items at once.
2. **`Option`/`Result` plus tagged unions.** Makes error handling first-class instead of a datac convention, and needs generics.
3. **`unsafe` plus FFI plus `repr(C)`.** Makes systems work, libc and C interop possible: the one reason Kelp today is "C with a mask".
4. **Threads plus `Mutex` plus atomics.** Servers, workers, real parallelism; the precondition for anything network-serious.
5. **`for`.** Makes ordinary code tolerable without touching the semantics.

Everything else, JSON, regex, LSP, GUI, ML, Decimal, certification, WASM, a registry, is either a library (writable once views and generics exist), a target (it comes with the backend), or a deliberate non-decision.

### 4. The honest consequence

Kelp will never do "everything", and that is the point. The languages that tried, C++, Scala and Swift among them, pay with compile time, specification size and a steep learning curve. Kelp's strength is not that it can do everything, but that it does **one thing right**: ownership plus capabilities in a small, explicit language. The useful version of Kelp is therefore not the largest one but the **most focused** one: a systems and application language for programs that take files, network, processes and security seriously, and that stays small enough to read in one evening.

## Far future additions

*The itemized lists (`A-1`-`A-17`, `B-1`-`B-10`, `C-1`-`C-4`, `D-1`-`D-5`, and the suggested order) are in the Backlog part below. They are a backlog, not a schedule: no numbers, no order, no commitment. What stays here is the part that is a decision rather than an item.*

**Three structural blockers.** Each one is a whole class of program the language cannot express today, and each one is why a block of backlog exists at all.

- **No `unsafe`** (B-3). No kernel, driver, allocator or runtime, and no escape valve for a deliberately conservative borrow checker.
- ~~**No user-declarable generics** (A-2, open item 34).~~ *Shipped as MK8-S1-M1 part 2.* Type parameters on `datac`/`enum`/`fun`, monomorphization at every use site, receiver methods on a generic type, explicit type arguments, and a `Map` with a real key type — so `Option`/`Result`, `datac Pair<A, B>` and a non-`String` map key are all expressible, and open item 34 is resolved. The list below is therefore **two** structural blockers, not three.
- **No runtime authority** (C-1, open item 18). Capabilities are compile-time constants and the entry module is unrestricted, so a *sandboxed* `kelpc` is not even expressible: a compiler's authority is runtime data (paths from `argv`, `PATH`/`CC`, temp files), not an allowlist.

**Three reversals of deliberate decisions.** These are not extensions. Each one undoes something v1 chose on purpose, and each needs an explicit decision before it becomes a task.

- **Allocators** (A-7, B-7): v1 has no custom allocator and no arena, and allocation failure panics. Reversed when a real program needs an arena or a fallible allocation.
- **Freestanding** (B-6): v1 assumes an ambient libc runtime (`stdio`, `malloc`, `atexit`, `main`). Reversed for a kernel, a firmware image, a bootloader or an embedded target.
- **Concurrency model** (B-4): v1 avoids a memory model by not having threads. Reversed *before* threads (MK6-S1-M1; see **Dependency notes**), not after.

Everything else in the backlog is an extension rather than a reversal, and lives in the Backlog part below.

### Blocks A–F: the far future, in detail

The two goals every block is read against are stated above in **Far future additions**: writing
`kelpc` itself in Kelp, and deep systems work (promoted to MK9). Neither is reachable with v1

#### A. Language surface required to write `kelpc` in Kelp

*A-1 to A-13 are promoted to MK8-S1 and MK8-S2; A-14 to A-16 and C-1/C-2 to MK8-S3; A-17 to MK8-S4 through MK8-S6. The items are kept here as the detail.*

- **A-1. Tagged unions and exhaustive pattern matching.** **Part 1 shipped as MK8-S1-M1 (part 1)**, recorded in `done.md`: the spelling is `enum` with payload-carrying variants, chosen over a `sum` keyword and over variants on `datac` because Rust's meaning of `enum` is exactly the meaning wanted here, while `datac` stays a record with one layout and one set of rules. What landed: `enum Name { Variant(val f: T) ... }` (variants newline-separated, the payload list shared with `datac`), construction as `Shape.Circle(r = 1.0)` / `Shape.Empty`, the `when <place> { Variant(bind) -> value else -> value }` pattern form (the boolean `when` has no scrutinee, so the two forms never collide), exhaustiveness checking that names a missing variant, payload binding by copy for `Copy` and by shared borrow otherwise, a C `tag` + `union` layout with a per-variant drop switch, enums as container elements, and one merged `datac`/`enum` declaration order. `syntax.md` §2.3/§3/§6.3/§9.2/§17 carry the syntax. What is left of A-1: nested/literal patterns and guards, which nothing needs yet. `Option<T>`/`Result<T, E>` still wait on A-2 (generics for the payload).
- **A-2. User-declarable generics.** **Shipped as MK8-S1-M1 part 2**, and open item 34 is resolved. Type parameters on `datac`/`enum` declarations, every use site monomorphizing into an ordinary named type; generic *functions* (`fun first<T>(xs: &List<T>).R: T`) and receiver methods on a generic type (`fun Pair<A, B>.first().R: A`); type arguments inferred from the arguments and from the expected type, with an explicit spelling at the expression when inference has nothing to go on (`Pair<i32, String>(...)`); inference through a nested generic constructor; and the builtin `Map` taking a key type (`Map<K, V>`, with `Map<V>` kept as the `String`-key shorthand). The key set is closed to `String`, the integers and `bool`, because the compiler generates the key's hash and its equality — a key of the user's own type would need a trait (A-12) or a comparator function (A-4), neither of which exists, and that is the one piece of "a `Map` with a real key type" that generics alone could not reach. `Box<T>`/`List<T>`/`Map<K, V>` remain compiler builtins.
- **A-3. `Option<T>`/`Result<T, E>` with propagation.** No `?`, no `if let`, no combinators, no null. The error-`datac` convention (stdlib decision 2) carries the stdlib and does not scale to a compiler: nested fallible calls become nested `if`s and every failure shape wants its own datac. This is MK5-S6-M1's decision point, and it is compiler ergonomics as much as stdlib surface. `?`/`if let` are syntax, so `syntax.md` gains them first.
- **A-4. Function values, closures, and move-taking parameters.** **Shipped as MK8-S1-M2 phases A-F, which close A-4.** `name: move T` takes ownership of its argument (open item 1's spelling), a declared `fun` is a value of type `fun(T).R: U`, a `fun` literal is written where an expression is expected, a literal that names a binding from the enclosing scope is a **closure** typed `closure(T).R: U` (a function value plus the heap environment its captures were moved into, dropped where the closure dies), a plain function value is widened into a closure where one is expected (through a generated shim when it names a function, so nothing is allocated), and `std/option`/`std/result`/`std/list` take callbacks that may capture. Every callback's payload is a borrow, so a call never moves an element or a payload out. **Nothing in A-4 is left**: the two pieces an earlier record listed as remaining — a `sort_by`-shaped comparator over an owned element type, and the helpers that hand an owned payload out by value (`option.unwrap` on an `Option<String>`, `result.map` over a `Result<T, MyErr>`, `list.filter` over a `List<String>`) — need **A-11's partial moves**, not closures, and are recorded there and in the modules' headers. A compiler is pass-structured `walk(node, |n| ...)`, comparators, diagnostic sinks, per-node callbacks — all of that is expressible now. MK5-S7-M1's two prerequisites (function values and a move-taking parameter) are met, and open item 60's (a)/(b) now cover closures as well, so MK6-S1-M1's language surface is no longer the blocker.
- **A-5. Iteration: a `for` loop, then possibly a protocol.** Open items 27, 36a and 46. **The cheap half shipped as MK8-S1-M3**: `for x in list { }` is a parser desugar to an index and a `while`, so a list walk no longer reads like C (the element binding is `List.get`'s — a copy for a `Copy` element, a shared borrow for an owned one). The reusable traversal (`iter`/`next`) is the expensive version and is **not** scheduled: it is what an abstraction over heterogeneous traversal would need, and nothing has asked for one. A-5 is therefore closed at the cheap form; the protocol stays an open question with no milestone.
- **A-6. A keyed container with non-`String` keys, and `Set`** (open item 41). A compiler's tables are keyed by interned symbol id, type id, node id, and `(module, name)` stringifying keys to reuse `Map<V>` is the wrong shape at the wrong cost, and `Map<bool>`-as-`Set` is a recorded stopgap rather than a substitute at compiler scale.
- **A-7. Shared ownership of immutable data, and allocator control.** No `Rc`-shape, no arena/region, and no custom allocator (all explicit non-goals today), while a `datac` field must be owned so interned strings, type tables and symbol tables can only be shared as *indices* into a `List`. Indexing is the standard compiler design and will work; the language gives no help, and with no allocator hook the allocation-heavy phase of compilation stays slow. An arena for AST nodes and a shared-immutable table type are the two things a compiler actually reaches for.
- **A-8. A length-carrying borrowed view, and borrows in fields** (open items 22, 29, 44). **The half that is a language feature shipped as MK8-S2-M1**: a builtin `View` — a pointer and a length, `s.view()`/`string.view()` to make one, `len`/`is_empty`/`get`/`slice`/`eq`/`to_string` on it, `print` emitting `%.*s` from the pair, and a `View` -> `String` copy where an owned value is expected. A slice is a pointer and a subtraction, a scan has its bound with it, and a function may return a view of its first reference parameter. **What did not ship, and why**: a `View` cannot be a *field*, an enum payload, a list element or a map key, because tying a stored borrow to its source needs lifetime syntax (A-11) — so "borrows in fields" stays open, and the parser that wanted to keep its input in a `datac` passes the view instead. **What also did not ship, and is stdlib work rather than a gap**: `path.parent`/`str.trim`/`str.prefix` still return owned values, and `List<String>.get(i)` still needs `.as_str()` — neither is a property of the type, both are signatures that would have to change. `syntax.md` §11.5 is the reference.
- **A-9. The bit surface.** v1 has *no bitwise operators at all* (the plan's own note: `str.char_at` does UTF-8 masks by subtraction), no char literal (open item 53), and no sized/hex/binary literal story. A lexer, a codegen and any byte-format work need shifts, masks and testable bits and `&` is already taken by borrows, so the spelling is itself a decision. **Shipped as MK8-S2-M1**: `&` `|` `^` infix, `~` prefix, `<<`/`>>` as two adjacent `<`/`>` characters, with the spellings resolved as predicted — `&` is bitwise-and in infix position and the borrow prefix in prefix position (C++'s reading), and the shifts are not lexed as one token so `List<List<i32>>` still closes. Precedence is C's *except* that the bitwise operators bind tighter than the comparisons, which is the one deliberate divergence: `flags & MASK == 0` means `(flags & MASK) == 0`. A char literal exists now too (open item 53). **Still open**: sized, hexadecimal and binary integer literals — integers remain decimal-only, and `fmt.hex` is the printing side.
- **A-10. Loosened container element rules** (open item 28). No `List<Box<T>>`, no `List<List<T>>`, no borrow or view elements, and a `datac` may only name earlier `datac`s (open item 12) a compiler's children lists are exactly the forbidden shapes, so today each one needs a wrapper `datac`.
- **A-11. Borrow-checker expressiveness.** Deliberately conservative, which is over-strict rather than unsound and a compiler is where the strictness lands hardest: no provenance, so a pointer local cannot be reused as a cursor (item 33); lexical lifetimes, so a bound borrow lives to the end of its block (item 30, workaround is an extra `{ }`); no NLL (a stretch goal only); no partial moves (the `Line` text case); no field-granular drop tracking and no flow-sensitive branch merge, which are also what the three deliberate leaks wait on (item 15). Eventually explicit lifetime syntax (`'a`), so a borrow can be a field and a type can say what it is tied to.
- **A-12. Traits/interfaces and dynamic dispatch.** Substitutable by enums for dispatch *if* A-1 exists, but not for destructors (a user `Drop`) and not for a pass abstraction ("a stage is a thing with a `run`").
- **A-13. Visibility/privacy.** Every top-level item of a module is reachable as `alias.Item` (MK2-S1-M1) and nothing in the plan adds `pub`. A ~100k-line self-hosted compiler with a fully public surface is a structural problem, not a style one.
- **A-14. Compilation at scale.** Separate compilation, incremental/query-based compilation, a cross-build cache, and a reserved internal-library location (today `impl` is local-files-only and `std/...` is the *compiler's* namespace). The measured baseline makes this a requirement rather than a nicety: ~95% of `kelpc build` is `cc`'s fixed overhead and Kelp's own pipeline is 3–4 ms (MK7's table), while a self-hosted `kelpc` is roughly an order of magnitude more Kelp source so MK7's own backend is a precondition for a tolerable self-hosted toolchain, not just a performance project.
- **A-15. Tooling.** A test framework (an explicit non-goal today), `kelpc fmt` (shipped — item 13, with its three recorded limits), a lint pass with the configurable naming option (item 23), and a documentation generator with doc-comment extraction.
- **A-16. Diagnostics and debuggability.** `#line` was never emitted (item 20), so generated code carries no source mapping; a real backend needs DWARF and a location story. Also an own tracing/profiling hook set, so a self-hosted compiler can be profiled without the C toolchain's help.
- **A-17. A bootstrap milestone, which this plan does not have at all.** Build `kelpc` in Kelp, compare stage0 (Rust `kelpc`) against stage1 (Kelp `kelpc`) on the whole fixture suite, then check the fixpoint (stage1 builds stage2, behaviourally or byte-identical). Without that test, "the compiler is written in Kelp" is a claim rather than a result the same standard the verification section already holds memory safety to.

#### B. Substrate required for deep systems

*Promoted to MK9 (see `roadmap.md`'s MK9 tables). The items are kept here as the detail.*

What separates a systems-*dialect* application language from a language that can host a kernel, a driver, a firmware image, an allocator or a runtime.

- **B-1. User FFI.** `extern fun` exists but is compiler-only: user code gets "only compiler-shipped stdlib modules may declare 'extern fun'" (MK3-S1-M2). Needs user-declarable externs, `extern "C"` blocks, variadic calls (MK7 stage 4 already flags the x86-64 SysV `AL`-register detail for `printf`), function-pointer/callback types, symbol import/export and linkage attributes, link flags and library paths, and system-library declarations (TLS, open item 37, is the first instance). Without this Kelp cannot call libc or any OS API no device library, no database client, no GUI toolkit.
- **B-2. ABI and layout control.** No `repr(C)`, no alignment, no packing, no unions, no bitfields, no explicit size/offset, no enum discriminants, no layout intrinsics (`size_of`/`align_of`/`offset_of`). So no MMIO register block, no wire or on-disk format, no packet header, no kernel struct, no C-interop struct the artefacts deep systems work is made of. MK7 stage 3 lists `datac` layout, calling convention, and `extern "C"` calls as *backend* work for the compiler's own ~20 externs; this item is the user-facing version of the same thing.
- **B-3. `unsafe`, raw pointers, and the memory surface.** No raw pointers, no pointer arithmetic, no casts/`transmute`, no `volatile`, no address-space or provenance control, no uninitialised allocation. Needed for MMIO, DMA, intrusive lists, allocators, page tables, kernel objects and lock-free structures. The plan's own evidence that Kelp cannot express this today is that `Bytes`/`String`'s runtime is a fixed C preamble in `codegen_c.rs` and the stdlib's primitives are 251 lines of C in `externs.rs`. With A-11's checker still conservative and no `unsafe`, there is also no escape valve the single structural reason a kernel is out of reach.
- **B-4. Atomics, ordering, and a published memory model.** No atomics, no fences, no ordering annotations, no `Send`/`Sync`-shaped discipline, and no definition of a data race because there are no threads. A systems language needs the model *before* the threads: what a `&mut` guarantees, what concurrent access to one location does, what a capability-protected region may be shared across, and what the compiler may assume. This is also the missing half of block D.
- **B-5. Threads, and then a concurrency story.** MK5-S7-M1's conclusion stands: no threads until function values *and* move-taking parameters exist (A-4), plus a rule for `&mut` crossing a thread boundary, owned data handed to a thread, per-thread stacks and TLS, a per-thread frame/cleanup story (drops are keyed to lexical blocks in one function), and what a panic in one thread does to the others. `async`/`await` is a further step and needs a state-machine transform in codegen. The intermediate that MK5-S7-M1 already ships is multi-process plus `poll`.
- **B-6. Freestanding / no-runtime mode.** Kelp assumes an ambient runtime: libc stdio, `malloc`/`realloc`/`free` from the preamble, `atexit` for owned `pd` drops, `main(argc, argv)`, and `kelp_panic` → `exit(1)`. Needs a `no_std`-shaped mode with no libc, no stdio and no implicit heap, a user-supplied panic handler and entry point, raw syscall access, target selection, linker-script/section control, static and shared library output, cross-compilation, and C-free static-ELF output. This is the requirement for kernel, bootloader, firmware, hypervisor, RTOS and embedded targets and MK7 stage 5's "static ELF with raw syscalls and our own runtime" is the same item approached from the toolchain side.
- **B-7. Allocator control.** A custom global allocator, per-arena/per-subsystem allocators, alignment and huge-page requests, DMA-safe allocation, and *fallible* allocation (`try_alloc`) today allocation failure panics and `mem.alloc(n)` is a fixed zero-filled `Bytes`. Arena/bump allocation and custom allocators are explicit non-goals in the current plan, so this item reverses that non-goal for the same reason A-7 wants an arena for the compiler.
- **B-8. Destructors and deterministic cleanup.** No user `Drop` (needs A-12), no `defer`, drops only at lexical scope exit and `atexit`, and a panic path that calls `exit(1)`. Systems code needs release points it can point at, a `Drop`-equivalent for resource handles, and a cleanup story for the panic/abort path which also means rethinking "a panic takes the process".
- **B-9. Hardware and ISA surface.** SIMD vectors, intrinsics, CPU-feature detection and dispatch, inline assembly, naked/interrupt-handler functions, calling-convention control (syscall, interrupt, fastcall), stack alignment and prologue control, atomics-as-instructions (with B-4), and cache/prefetch hints. Without these there is no lock-free primitive, no context switch, no device ISR and no vectorised kernel.
- **B-10. Data-format primitives.** Endianness conversion intrinsics, unaligned load/store, and byte-order-aware reads and writes, so a wire or on-disk format is expressible without hand-rolled shifting (which A-9 is also needed for).

#### C. Capability-model gaps (this language's headline, extended)

*C-1 is promoted to MK10-S2, C-2 to MK8-S3, and C-3/C-4 to MK10-S1 and MK10-S3. The items are kept here as the detail.*

The capability system is the differentiator, and it is currently a compile-time constant allowlist plus an unrestricted entry module. Two consequences matter for anything beyond one sandboxed program.

- **C-1. Runtime-derived authority.** A real `kelpc` takes its authority from runtime data: source paths on `argv`, the project root, `PATH`/`CC`, a temp directory, an arbitrary `cc` binary. Kelp cannot express "this authority came from my input": grants are compiled-in patterns, no module ever holds a capability *value* it could pass or attenuate, and there is no runtime delegation. Needs capability values/handles as a first-class (or explicitly restricted) thing plus a rule for deriving a pattern from runtime input safely otherwise `main` stays unrestricted and the headline feature is off for the compiler, which is the state today.
- **C-2. Restricting the entry module** (open item 18): `coral.toml [caps]`, so `main` can hold less than everything. The capability fixtures already work around this by putting their interesting module behind one level of delegation.
- **C-3. Device and kernel vocabulary.** Grants for device nodes, MMIO regions, IRQ lines, kernel object handles, memory regions/pages, and file descriptors *as capabilities* rather than as names the object-capability reading the model is already shaped for (seL4/Fuchsia-like), and the direction that would make capabilities a systems feature rather than a sandbox one.
- **C-4. Attenuation and per-request grants.** Handing a narrower grant to a plugin or worker at runtime (the multi-process story MK5-S7-M1 ships), revoking one, and bounding a grant's lifetime and holder count.

#### D. Verification and semantics duty

*Promoted to MK11. The items are kept here as the detail.*

Cross-cutting, and the reason the current claims cannot simply be extended to unsafe or concurrent code: every memory-safety and capability claim in the verification section is verified *through clang* (ASAN, `-fwrapv`). Once there is `unsafe`, raw pointers, atomics, or an own backend, the obligation transfers to Kelp, and the argument has to be about Kelp's semantics rather than C's.

- **D-1. A formal operational semantics, and an aliasing model for `&mut`** a Stacked-Borrows/Tree-Borrows equivalent, or a documented decision not to have one. The borrow checker's rules are implemented across `infer.rs`/`borrowck.rs`; the model they implement is not written down anywhere.
- **D-2. A UB catalogue.** Defined behaviour for overflow (currently `-fwrapv` from the C toolchain), uninitialised memory, out-of-bounds, provenance, the FFI boundary, and data races (once B-4 exists). "No UB" cannot be claimed against an undefined model.
- **D-3. A Miri-equivalent dynamic checker** (or a proving argument) for the move/borrow/aliasing rules, so soundness is a test result rather than a reading of the checker's source.
- **D-4. Conformance, differential testing and fuzzing.** A grammar/conformance corpus, differential runs of two backends over the same fixtures (MK7 stage 1's `--backend=` flag is the seed of it), and fuzzing of the lexer, parser and checker against the semantics.
- **D-5. Own sanitizers and debug info.** DWARF emission, source mapping (A-16), and a sanitizer story that does not depend on clang.

#### E. Suggested order, and cost

*Block E calls A-7/B-7 (allocators), B-6 (freestanding) and B-4 (concurrency model) decisions to make rather than tasks to schedule. Those three are MK9-S5, MK9-S4 and MK9-S3 the decision is now made inside a tracked Mark.*

Nothing here is scheduled. If it ever is, the cheapest useful sequencing is:

1. A-1 to A-5 and A-11 unions/patterns, generics, `Option`/`Result`, function values, iteration, and checker expressiveness. Without them a self-hosted front end is not writable at all, and A-1 is the largest single language change since borrow checking. (A-1 to A-5 have shipped; what is left of this step is A-11.)
2. A-6 to A-13 containers, shared data/arenas, views, bits, element rules, traits, privacy. The ergonomics that make a large body of Kelp code tractable.
3. A-14 to A-17 with C-1 and C-2 scale, tooling, bootstrap, capability derivation. The difference between "self-hosted in principle" and "self-hosted and usable".
4. B-1 and B-2 FFI and layout. The first *systems* unlocks, and partly free from the C backend if only they were exposed.
5. B-3 to B-10 unsafe, atomics/model, threads, freestanding, allocators, destructors, ISA. Each one a subsystem; together, the difference between a systems-dialect language and a systems language.
6. Block D runs alongside from the first `unsafe`, and B-4 (the memory model) is a precondition for honest claims about B-3, B-5 and B-9.

For calibration: A-1, A-2, A-4, B-3, B-6 and B-9 are each larger than the entire MK5-S1–MK5-S7 stdlib program, and A-14 compounded with MK7 is a project of its own. Three items are reversals of deliberate decisions rather than extensions A-7 and B-7 reverse "no custom allocators, no arena", B-6 reverses "assume an ambient libc runtime", and B-4 creates the concurrency model v1 avoids on purpose. Those should be treated as decisions to make, not tasks to schedule.

#### F. Dependency and precedence notes

- **The precedence rule still applies: `syntax.md` wins on syntax and style.** Any syntax these blocks need a sum type, `unsafe`, `repr`, `'a`, `View`, `defer`, `?`, `if let`, `trait` must be added to `syntax.md` first, because that file is the authority on syntax and this one is not. (`for` was on this list and is the one entry that has since shipped, as MK8-S1-M3, with `syntax.md` §6.2 edited first.)
- **Open items these blocks close or supersede**: 4 (`when` value patterns), 11 (line continuation, if syntax work starts), 12 (a datac naming only earlier datacs), 13 and 23 (`kelpc fmt`/lint), 15 (the three deliberate leaks, via field-granular drop plus a flow-sensitive merge), 18 (`main` unrestricted), 20 (`#line`/debug), 28 (element rules), 29, 30 and 33 (borrow lifetimes, provenance, bound-borrow scoping), 34 (generics), 36c (`Option`/`Result`), 37 (TLS, as the first FFI/link case), 41 (`Map` keys, `Set`), 44 (a length-carrying view), 53 (`char`). Three that were on this list — 27, 36a and 46 (`for`) — closed early, as **MK8-S1-M3**: the cheap loop shipped as a parser desugar, and only the `iter`/`next` protocol is still a question.
- **The structural blockers, restated**: see **Far future additions** above for the three, and why the first two are also the reason A-2 sits on the critical path.
- **What is not in this backlog, on purpose**: GC or exceptions (both permanent divergences, `syntax.md` §13), and a REPL/LSP/IDE story (unscoped in this plan entirely, and downstream of A-1 to A-17). A package registry and third-party dependencies were on that list; they are now the Coral design's decision (roadmap open item 72) rather than a settled non-goal, with path and git dependencies paying off whether or not an index ever exists.

### Coral: the build tool and package manager (roadmap open item 72)

*The `MK13-Sn-Mn` identifiers below are the ones this design carried when it was a Mark. They are kept so the detail stays addressable. Nothing here is scheduled.*

*Scope: the project layer above the compiler. `kelpc` stays the compiler. Coral owns the manifest, the project layout, the task graph, dependency resolution, the build cache, artifacts, the test runner, formatting and publishing. Modeled on Gradle: a project model, tasks with declared inputs and dependencies, a build cache, and a development/release split. Named Coral.*

Why this exists, in this repository's own evidence: `kelpc build <path>` compiles one `.kp` file or one directory containing `coral.toml`, and stops there. Everything beyond that is currently someone's shell script or Rust test code. `bench/speed/run.sh` is a 120-line shell program that assembles flags, runs each workload five times, and formats a table. `kelpc/tests/compile_and_run.rs` reimplements discovery, per-fixture flags, expected output, and an AddressSanitizer pass. `examples/download.kp` documents its own build command in a comment. Each of those is a build-tool task that has been hand-written once and will be hand-written again by the next project.

**Division of labor.**

- **`kelpc` keeps the compiler jobs**: load the module graph, type check, move/borrow check, emit C, invoke `cc`, and from MK7 emit machine code. `kelpc build` and `kelpc run` stay documented low-level commands.
- **Coral owns the project**: manifest, layout, tasks, profiles, dependencies, cache, test runner, artifact naming, publishing, toolchain pinning.
- **Coral calls `kelpc`, never the reverse.** Everything Coral needs from the compiler is a command-line contract, not a link against compiler internals.

**Tasks are Kelp programs, and that is the design.** Gradle needed a scripting language, then a DSL, then a plugin API, because a task is arbitrary code. Kelp already has arbitrary code: a task is an `.kp` file with `fun main()`, run by Coral, and its authority is whatever its own `impl` lines grant. No scripting DSL, no dynamic plugin API, no build logic inside a string. A task that reads data and writes a report declares exactly that, and the capability checker enforces it:

```kelp
// tasks/report.kp
impl "std/fs" with caps(fs = ["/project/out/**", "/project/data/**"])
impl "std/str"
impl "std/fmt"

fun main() {
    val size = fmt.uint(fs.size("/project/data/input.csv"))
    fs.write_text("/project/out/report.txt", str.concat("input bytes: ", size.as_str()))
}
```

The manifest names it, and Coral runs it:

```toml
# The shape Coral grows coral.toml into. Today's manifest is flat, has four keys
# (name, version, entry, http_pool), rejects every section, and rejects an
# unknown key, so this is a format change with a compatibility story to decide
# (open item 66).
[package]
name = "myproject"
version = "0.1.0"
entry = "src/main.kp"

[tasks]
report = { file = "tasks/report.kp" }
docs   = { file = "tasks/docs.kp" }
```

```sh
coral init myproject       # coral.toml, src/main.kp, tests/, .gitignore
coral build                # dev profile, artifacts in build/
coral build --release
coral run -- data.csv      # argv and exit code pass through
coral task report
coral test
coral fmt --check
coral clean
```

**Deliberately not in Coral**: a scripting language (tasks are Kelp), a dynamic plugin runtime (extensions are manifests and Kelp programs), and a general version-range solver (nothing carries a version by design — a dependency is a git remote, or one folder inside one — and ranges stay MK13-S3-M3's problem).

**What has shipped since the sketch** (`coral` repo, tagged `v0.3.0`): `coral init`/`build`/`run`/`check`/`clean`, `[tasks]`, `[dependencies]` fetched from the Gitea over SSH, the fingerprint build cache, and toolchain management. The last of those is **MK13-S6-M1**'s second half — per-project selection: `[toolchain] kelp = "v0.1.1"` in `coral.toml` names the compiler a project builds with, resolved as `$KELPC`, then the pin, then `~/.coral/bin/kelpc`, then `PATH`, with a pinned version that is not installed yet installed on the spot. `coral toolchain kelp pin <ver>` writes that one line in place (comments and section order survive it, and `kelpc` never sees it — the section is after the first `[`), `pin --clear` removes it, `installed` lists what is on disk, and `coral init --kelp <ver>` writes it at scaffold time. `coral v0.5.0` then made the store single-version: `install` and `use` drop every other version of a component once the new binary is in place, so a pin that is not the stored version displaces it (one reinstall per switch for two projects pinned differently) rather than accumulating toolchains. `coral toolchain kelp|coral install <ver>` prefers the tag's own release binary — the `kelpc-0.1.1-linux-x86_64` asset on kelp's `v0.1.1` release, downloaded with `curl` into `toolchains/<component>/<ver>/<binary>` — and falls back to `git clone --branch <ver> --depth 1` plus `cargo build --release`, which is what still makes `v0.1.0` (a tag with no release) installable.`coral v0.5.1` then dropped `coral add`, `coral update` and `coral.lock` outright — a Kelp library has no version, so a dependency is a manifest line and `coral sync` is what fetches and refreshes it — and `coral v0.5.4` made a dependency nameable as one **folder** inside a repo (`Juniper/fpl/sillyname`), fetched with `--filter=blob:none --sparse` and copied flat into `src/deps/<name>/`, so a sibling library in that repo never comes down. Workspaces, `coral test`/`fmt`/`lint`/`bench`, publishing and version ranges are still the sketch.

**What Coral needs from elsewhere.**

- **From the compiler**: machine-readable diagnostics, a module dependency list, separate compile and link steps, and a stable CLI contract (MK13-S1-M3). Today `kelpc build`/`kelpc run`, `kelpc version` (added with the 0.1.1 release) and prose diagnostics are all a build tool has to work with.
- **From MK5-S2-M1 (done)**: `process.spawn`, argv, captured output and exit codes, which Coral and every non-trivial task need.
- **From MK8-S1/S2, only if Coral is written in Kelp**: generics, `Option`/`Result`, function values and containers — **all four shipped** (A-2 as MK8-S1-M1 part 2, `Option`/`Result` as MK5-S6-M1, containers as MK3, function values and closures as MK8-S1-M2 phases A-F), so the language half of open item 67 is met. Until Coral is ported it is a Rust program that drives `kelpc`.
- **From MK9-S4-M2**: cross-compilation and library output, which MK13-S4-M2/M3 extend rather than invent.
- **From the capability model (MK4-S1-M1, done)**: task grants are checked the same way module grants are, which is what lets a build task hold less authority than the user running it.

#### What the port hit: three stdlib-sized gaps, all three now shipped

Writing the parts of Coral's Rust that shell out (`deps.rs`, `toolchain.rs`) against this stdlib ran into four things. Three were stdlib additions and **all three shipped as MK5-S2-M2** (the `fs.symlink` half continuing MK5-S5). None of them needed a language feature: the surface all of them would be written against — generics, `Option`/`Result`, containers, function values — was already shipped. The fourth was a language gap, and MK8-S1-M2 phases E-F closed it. The rows are kept as they were written, with what shipped recorded against each.

| Gap | Evidence | Workaround today | Fix | Size |

| ~~**No `chdir`, and no per-call working directory.**~~ | *Done — **MK5-S2-M2**.* As written: `std/process.kp`'s `run` said it outright ("There is deliberately no `chdir` in v1: a process-wide working directory would make every grant pattern's meaning depend on mutable global state"), and Coral runs `git`/`cargo` inside specific target directories constantly, with `git -C`/`cargo --manifest-path` covering two tools and nothing else. | — | Shipped exactly as the sketch had it: `spawn_in(dir, program, args)` / `run_in(dir, program, args)`, `chdir` in the **child** between `fork` and `exec` (one branch in `spawn_raw`'s child path, plus the `dir` parameter), with `spawn`/`run` reduced to delegates passing `""`. Two precisions the sketch asked for and got: the failures are decided **before the fork** by `stat`/`access` (so `NotFound` means the path names nothing and `NotExecutable` means something is there that `exec` would refuse, and neither can be confused with a child exiting with a matching code), and `run("git", ...)` still has no `PATH` search — the check refuses a relative program, so resolving through `PATH` is the caller's job and stays out of the stdlib. **`NotAbsolute` and `Denied` did not ship**: both are refused by the compiler's call-site check, which panics, so neither is reachable from Kelp (open item 73 records the codegen change a value-returning denial would need). The pattern in all three gaps was the same: the primitive was missing, the *shape* of it was already decided by the module that would gain it (`spawn_in` by `run`'s own doc comment, `try_run` by the `Option`/`Result` convention MK5-S6-M1 established for every other fallible stdlib call), and each was one extern plus one wrapper. To that the implementation added one place the estimate was wrong: the *capability* table, not the C, is what the `_in` forms moved — `checked_args` is keyed on the call's name now, so a working directory is never matched against a program allowlist. The one thing the compiler had to refuse outright is a value-returning grant denial (open item 73).
